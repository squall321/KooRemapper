# CI 에 gmsh 를 깔아야 한다 — 이 리포의 토큰으로는 푸시가 안 된다

**작성일**: 2026-09-25
**한 줄**: `0704b79`·`2e47878` 이후 **CI 가 빨갛다.** 고칠 패치는 옆에 있는데
`.github/workflows/` 는 이 세션의 토큰 권한으로 못 올린다.

## 무슨 일인가

덱 계약 2차 P0-3 에서 "gmsh 가 없으면 **skip 이 아니라 FAIL**" 로 바꿨다. 그 skip 안에 실제
결함(`meshfix` 의 CRLF 소실·2줄 포맷 요소 소실)이 숨어 있었고 실사용 박스가 우리보다 먼저
찾아 돌려줬으니, 조용히 건너뛰는 길을 없앤 그 수정 자체는 옳다.

그런데 `.github/workflows/regress.yml` 은 gmsh 를 깔지 않는다. 그래서 그 커밋 이후
**`test_meshfix_two_line.py` 와 `test_newline_matrix.py` 가 CI 에서 실패한다.**
워크플로 주석은 아직 "gmsh 를 쓰는 항목은 시험 쪽에서 스스로 SKIP 을 찍고 넘어간다" 고
적혀 있다 — 그 계약을 내가 깬 것이다.

## 왜 여기에 문서로 남기나

푸시가 거부된다.

```
! [remote rejected] main -> main
  (refusing to allow a Personal Access Token to create or update workflow
   `.github/workflows/regress.yml` without `workflow` scope)
```

이 제약은 어느 ref 로 밀어도 같다. 그래서 패치를 리포에 실어 둔다 — 재부팅 때 개발 트리가
`reset --hard origin/main` 되므로, 커밋 안 된 변경은 그대로 사라진다.

## 적용하는 법

둘 중 하나면 된다.

1. `workflow` 스코프가 있는 토큰으로:
   ```bash
   git apply docs/requests/ci-gmsh-2026-09-25.patch
   git add .github/workflows/regress.yml
   git commit -m "fix(CI): gmsh 를 깐다 — skip 을 FAIL 로 바꾼 뒤 CI 가 빨갛다"
   git push
   ```
2. GitHub 웹 편집기에서 `.github/workflows/regress.yml` 을 직접 고친다(패치 내용 그대로).

## 패치가 하는 일

- `apt-get install -y ... gmsh` 추가. `meshfix` 가 쓰는 `.geo` 기능(`Merge` ·
  `ClassifySurfaces` · `CreateGeometry` · `Surface{:}`)은 gmsh 4.0+ 이면 된다 —
  apt 판(4.8~4.11)으로 충분하다.
- 회귀 단계에 `KOOREMAPPER_GMSH=/usr/bin/gmsh` 를 준다. **경로를 고정하는 것이 핵심이다** —
  PATH 탐색에 맡기면 어떤 gmsh 를 집었는지로 결과가 갈린다. 이 리포에서 실제로 그랬다
  (개발 박스의 `~/.local/bin/gmsh` 는 깨진 파이썬 래퍼라 meshfix 가 rc=1 로 죽는다).
- `KOOREMAPPER_TEST_GMSH` 는 **일부러 안 준다.** 주면 `test_gmsh_discovery.py` 가 플랫폼 배치
  갈래까지 돌게 되는데, 그 시험은 지금 '없으면 건너뛴다' 를 스스로 선언한 상태다.
  이 변경의 범위를 넘으므로 켤지는 따로 판단한다.
- 낡은 주석("SKIP 을 찍고 넘어간다")을 실제 계약으로 고친다.

## 남는 위험

apt 판 gmsh 로 `meshfix` 가 실제로 도는지는 **첫 CI 실행으로** 확인된다. 이 박스에서는
`KOOREMAPPER_GMSH` 만 준 상태로 세 시험이 전부 통과한다(gmsh 4.14.1). 버전 문제가 있으면
CI 가 그 사실을 분명히 말할 것이고, 지금처럼 원인을 알 수 없는 실패로 남는 것보다 낫다.
