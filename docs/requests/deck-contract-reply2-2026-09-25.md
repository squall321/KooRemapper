## 0. 먼저 — 그쪽이 옳았다

§3 의 지적("전부 통과가 전부 돌았다는 아니다")은 맞았다. 우리가 `meshfix` 를 못 본 이유는
코드 차이가 아니라 **실행 환경 차이**였다는 진단도 맞다. 더 중요한 것은 그 지적이 우리
시험의 **구조적 구멍**을 가리켰다는 점이다 — 건너뜀을 통과와 구분해 출력하고 있었지만,
건너뜀 자체를 **아무도 판정하지 않았다.**

그 자리를 전수로 뜯었더니 건너뜀 29는 한 덩어리가 아니라 셋이었다.

| 부류 | 수 | 정체 |
|---|---|---|
| ① 예제 폴더에 입력 덱이 없다 | 16 | 카탈로그의 파일 이름은 **프런트 폼 자리표시자**다. 실제 덱은 다른 폴더·생성물·리포에 없는 것 |
| ② **판정이 틀렸다** | 6 | 로그는 `Done -> xxx.k` 인데 "새 덱 0개". 산출물 이름이 예제 폴더에 이미 있어, op 이 **바이트 동일하게** 다시 쓰면 해시가 같아 "안 바뀐 입력" 으로 걸러졌다. 이건 실패가 아니라 **보존**이다 |
| ③ 정말 덱을 안 쓴다 | 7 | `info`·`strain`·`generate` 계열 등 |

②가 특히 뼈아프다 — 우리는 **통과를 건너뜀으로 세고 있었다.** 내용 해시만 봐서는 "건드렸나" 와
"바꿨나" 가 안 갈린다. 지금은 mtime 기준선과 내용 해시를 **둘 다** 본다.

## 1. 정정 2건

### ① `requires_gmsh` 는 `meshfix` 하나, `requires_tetgen` 은 49개 전부 false

카탈로그(`platform/core/kooremapper_core/catalog_data.json`) 전수 확인이다. op 은 정확히
49개이고 `requires_gmsh: true` 는 `meshfix` 하나다.

**다만 그대로만 읽으면 오해를 부른다.** `requires_tetgen` 이 전부 false 인 것은 "외부 tetgen
실행 파일을 요구하는 op 이 없다" 는 뜻이다. tetgen 은 AGPL v3 때문에 빌드 옵션(기본 OFF)으로만
들어가며 **지금 배포 바이너리에는 없다.** 컨테이너에 tetgen 을 넣어 달라는 요청은 필요 없다.

### ② `api.sif` 안에 gmsh 가 없다 — 그리고 기전은 로그인 셸이다

실행으로 확인했다(컨테이너 실행이 막히지 않았다).

- `--no-home --cleanenv` 에서 `sh -c 'which gmsh'` → rc=1. 이미지 안에 gmsh 실체가 0건이다.
- 도는 인스턴스에서 `bash -lc 'which gmsh'` → `/home/koopark/.local/bin/gmsh` (rc=0)
- **같은 인스턴스에서** `sh -c 'which gmsh'` → rc=1

즉 "홈 바인드" 만으로는 설명이 반쪽이다. 정확히는 **바인드된 홈의 `~/.profile` 이 PATH 에
`~/.local/bin` 을 앞세우므로 로그인 셸에서만 잡힌다.** 그리고 거기 있는 것은 gmsh 가 아니라
**깨진 파이썬 래퍼**다(`#!/usr/bin/env python` 로 시작하고 import 에서 죽는다).

그래서 해법은 "컨테이너 안에서 회귀를 돌린다" 가 아니라 **`KOOREMAPPER_GMSH` 고정**이다.
탐색 순서가 `$KOOREMAPPER_GMSH` → `<exe>/gmsh/` → PATH → `/opt/gmsh-*` 이므로
(`src/commands/meshfix.cpp` 의 `findGmshExe`, 2026-09-25 기준 :217-), 환경변수만 고정하면 PATH 에 무엇이 있든 결과가 안 갈린다.

## 2. 새 결함 3건

### ③ 개행을 잃던 자리는 **10곳이 아니라 12곳**이었다

먼저 9개 op 이 입력 덱의 개행을 잃고 있었다. 실측(CRLF 덱 입력 → 산출 덱)이다.
표의 줄 번호는 **고치기 직전**의 것이다(커밋 `afbc154`·`e841e5a` 기준) — 지금 HEAD 에서 찾으면
밀려 있다. 자리를 되짚으려면 그 커밋을 보시라.

| op | 산출 덱 | 자리 |
|---|---|---|
| `explicit` | CRLF 0 / LF단독 86 (전멸) | `implicit.cpp:209` |
| `implicit` | CRLF 86 / LF단독 15 (**혼재**) | `implicit.cpp:322,454` |
| `modal` | CRLF 0 / LF단독 95 | `modal.cpp:161,252` |
| `stabilize` | CRLF 0 / LF단독 89 | `stabilize.cpp:544` |
| `database` | CRLF 0 / LF단독 169 | `database.cpp:403` |
| `hfdamp` | CRLF 0 / LF단독 132 | `hfdamp.cpp:639` |
| `optimize` | CRLF 0 / LF단독 63 | `optimize.cpp:413` |
| `cclip` | CRLF 0 / LF단독 281 | `cclip.cpp:1695` |
| `squeeze` | CRLF 73 / LF단독 2 (**혼재**) | `squeeze_assemble.cpp:452` |

`implicit`·`squeeze` 는 **한 파일 안에서 개행이 갈린다** — 원본 줄은 CRLF, 새로 끼운 카드만
LF 다. 리뷰가 `relax` 에서 최악이라 짚은 그 모양이다.

그리고 여기서 멈추지 않고 소스의 `std::ofstream` 30곳을 전수 분류하니, **예제가 안 켜는 옵션**
뒤에 셋이 더 있었다.

- `cclip.cpp:1659` — `stress_output: include` 의 dynain
- `cclip.cpp:1684` — `free_output: true` 의 `_free.k`
- `squeeze_assemble.cpp:232` — `strain_mode` 의 dynain

**dynain 이 갈리는 것이 특히 나쁘다.** `*INCLUDE` 로 본 덱과 **함께 풀리는 짝**의 개행이
어긋난다. 리포 안에 올바른 구현이 이미 있었다(`DynainWriter.cpp:106-108` 이 바로 그 이유로 원본 개행을 따른다) — 셋만 빠져 있었다.

> **별도 문단 — `matswap`·`strip` 2곳은 리눅스 산출물이 바뀌지 않았다.**
> 이 둘은 리눅스에서 CRLF 를 지킨다. 고쳐서가 아니라 **그 리더가 `\r` 을 안 떼기** 때문이다.
> 그래도 공용 라이터로 옮겼는데, 이유는 **MSVC 텍스트 모드에서 그 경로가 `\r\r\n` 을 내기**
> 때문이다. 리눅스에서 재현을 시도하면 안 나오니 위 12곳과 섞어 세지 마시라.

### ④ `meshfix` 가 2줄 포맷 덱에서 **다른 파트의 요소를 조용히 없앤다**

`spliceMesh` 가 줄마다 첫 정수를 읽어 삭제를 정했는데, `*ELEMENT_SOLID` **2줄 포맷**에서
둘째 줄의 첫 정수는 **노드 번호**다. 그 값이 삭제 대상 EID 집합에 우연히 들어 있으면
**건드리지 말아야 할 파트의 노드 줄만** 지워져 요소 카드가 헤더만 남는다.

재현(수정 전) — `examples/mesh/tetramesh.k`(이미 2줄 포맷이다)에 노드 번호가 PID 1 의 EID 와
겹치는 PID 2 카드 3개를 붙이고 `meshfix pid:1`:

```
원본      Elements 28416 / Parts 2
수정 전   Elements  1908                ← PID 2 의 3개가 사라졌다
수정 후   Elements  1911                ← 이 박스 실측(회귀 픽스처: PID 2 카드 3개)
산출물 원문(수정 전)은 이렇다.
    900001       2
    900002       2                      ← 노드 줄이 없다
    900003       2
그런데 info 는 [OK] Mesh is valid · rc=0
```

> 계획서 초안에 적혔던 **1913 은 쓰지 마시라** — 그 수는 PID 2 카드를 5개 붙인 픽스처의 값이고,
> 회귀 시험은 3개를 쓴다. 회귀가 단언하는 것은 **요소 수가 아니라 헤더–노드 줄 짝**이다
> (gmsh 재메싱 수는 환경에 따라 흔들릴 수 있어 수치 단언을 일부러 안 했다).

셋이 겹쳐 최악이었다 — ① 리포의 meshfix 예제 덱이 이미 2줄 포맷이다 ② meshfix 는 자체
라이터라 요소 수 대조 게이트를 안 거친다 ③ `info` 가 통과시킨다. 캠페인 사건 1(A27 요소
소실)과 같은 모양이다. 올바른 구현은 리포에 이미 있었다 — `cclip.cpp` 의 `cc_removeSolidElements`(2026-09-25 기준 :814).

**왜 우리 시험이 놓쳤나** — `meshfix` 는 `requires_gmsh` 인 유일한 op 이고, gmsh 가 없으면
건너뛰었다. 그쪽이 짚은 바로 그 자리다.

### ⑤ 판정이 **바이너리가 어디 있느냐**로 갈린다 — `meshfix` 와 `matdb` 둘 다

같은 sha256 바이너리·같은 덱·같은 PATH 에서 **위치만** 바꿔 돌린 실측이다.

```
build/linux/bin/KooRemapper       → Gmsh: /home/koopark/.local/bin/gmsh
                                    [ERROR] Gmsh failed (exit 32512) · rc=1 · 산출물 없음
platform/backend/bin/KooRemapper  → Gmsh: .../platform/backend/bin/gmsh/gmsh.exe
                                    [OK] Gmsh done · rc=0
```

같은 모양이 `matdb` 에도 있다. 번들 재질 DB 를 `작업폴더 materials/` → `<실행파일>/materials/`
→ `<실행파일>/../materials/` 순으로 찾으므로(`ModelAssembler.cpp` 의 `md_findBundledDb`, 2026-09-25 기준 :12529 — `/proc/self/exe` 기준), 배포 트리에서는 통과하고 빌드 트리에서는 rc=1 이다.

그쪽이 §3 에서 "옛 바이너리로 ALL OK" 의 정체를 물었는데, 답이 이것이다 — **어느 복사본을
시험에 줬느냐**다. 결론은 하나다. **시험·CI·컨테이너는 의존물 경로를 환경변수나 절대 경로로
고정해야 하고, 바이너리 옆에 무엇이 있느냐로 판정이 갈리는 배치를 판정 근거로 쓰면 안 된다.**
우리 쪽 매트릭스는 이제 리포의 `materials/` 를 작업 폴더에 직접 갖다 놓고 돌린다.

## 3. 아직 안 알린 동작 변경 3건

하류가 rc 로 판단하므로 먼저 알린다. pyKooCAE REMAP 스텝은 rc≠0 이면 그 스텝을 failed 로
기록하고 **시나리오 전체를 중단한다**(`CumulativeScenarioRunner.py:2261-2267`, 체인 루프 `:866-890`).

### ⑥ `e2281b3` — 폭을 못 맞추면 자르지 않고 rc≠0

**범위는 `assemble` op 의 `control:` 블록 한 곳이다**(독립 `control` op 은 카탈로그에 없다).
값이 10칸에 안 들어가면 이제 rc=1 이고 **출력 덱을 아예 쓰지 않는다.** 예전에는 잘라 쓰고 rc=0 이었다.

왜 바꿨나 — `dt2ms` 부호 소실 때문이다. 음수가 선택적 질량스케일링, 양수가 고정 dt 스케일링이라
**부호 하나로 물리가 뒤바뀌는데** 구조 카운트는 전부 정상이었다.

> 되묻는다 — `assemble` 의 `control` 에 10칸을 넘기는 값을 넣던 시나리오가 있나.

### ⑦ `d194c49` — ORTHO/COMPOSITE 배치 거절

**범위는 `cnrb2spring` op 하나다.** 거절 조건 셋 — 지원하지 않는 요소 키워드 · 노드 카드 뒤에
고정 카드가 더 붙는 변형(`_ORTHO`·`_DOF`) · 줄 수가 데이터로 정해지는 변형(`COMPOSITE` 계열).
만나면 추측하지 않고 rc=1 로 멈추며 출력 파일을 쓰지 않는다.

**옛 동작을 함께 적는다** — 예전에는 엉뚱한 파트 쌍에 체결부를 달고 rc=0 이었다. rc 가 1 로
바뀐 것이 개선인 이유가 그것이다. 공용화하지 않고 op 안에 둔 것은 의도다 — `KFileReader` 는
49개 op 전부의 입구라 거기서 거절하면 파급이 너무 크다.

### ⑧ `814ff72` — `info` stdout 에 `[ERROR]` 가 나지만 rc 는 0

실측 네 줄이다 — rc=0 · stdout 에 `[ERROR]` · stderr 0바이트 · 같은 출력에 `[OK] Mesh is valid` 공존.

하류 기준으로 말하면, 플랫폼 잡은 `exit_code` 만 보므로 **이 덱도 succeeded 로 남는다.**
LS-DYNA 는 Error 10144 로 키워드 단계에서 멈출 덱이다.

> **덧말** — `[ERROR]` + rc=0 조합 자체는 이번에 처음 생긴 것이 **아니다**(기존 validation 실패
> 분기도 그랬다). 늘어난 것은 그 `[ERROR]` 를 내는 **사유**다. 그쪽 로그 파서가 stdout 의
> `[ERROR]` 를 실패로 세고 있었다면 지금까지도 오탐이 있었다는 뜻이다.
>
> 되묻는다 — 제출 로그 파서가 stdout 의 `[ERROR]` 를 실패로 세나.

## 4. 우리 쪽 시험의 새 계약

`test_newline_matrix.py` 는 이제 **건너뛰지 않는다.**

> 49개 op 중 **42개를 판정하고 7개는 이름과 사유를 소스에 선언해 제외한다.**
> 건너뜀은 **0** 이고, 판정 없이 끝나면 **FAIL** 이다.
> 제외 7개 — `info`(읽기 전용) · `strain`(CSV) · `modelmeta`(JSON) · `stcx_fullangle_drop`(외부 제출) ·
> `generate` · `generate-var` · `battery`(셋 다 덱을 새로 만든다 — 보존할 원본 개행이 없다)

`requires_gmsh` 인데 gmsh 가 없으면 **skip 이 아니라 FAIL** 이다. 그쪽이 찾아낸 바로 그 구멍이다.

그리고 소스 축 관문을 하나 더 뒀다 — `src/`·`include/` 의 `std::ofstream` 을 파일별로 **선언**하고,
수가 달라지거나 선언에 없는 파일에서 나오면 FAIL 이다(분류는 덱(보존)·덱(신규)·덱 아님).
예제 기반 시험은 **예제가 안 켜는 옵션**을 못 보기 때문이다 — ③의 뒤쪽 3곳이 그 증거다.

### CI 는 아직 이것을 지켜 주지 않는다

정확히 적는다. **이 박스에서는** gmsh 를 고정해 돌려 회귀 46개가 전부 통과한다.
**CI 러너에는 아직 gmsh 가 없고** `dist/gmsh` 는 저장소에 없으므로, gmsh 가 필요한 두 시험은
지금 CI 에서 실패한다. 고치는 패치는 만들어 두었으나 워크플로 파일은 토큰 권한 때문에
아직 못 올렸다(`docs/requests/ci-gmsh-2026-09-25.md` 에 패치와 적용법을 남겼다).
**"CI 가 막아 준다" 고 믿고 그쪽 검증을 줄이지 마시라 — 아직 아니다.**

검증 방식은 이렇다. 고친 자리를 하나씩 되돌려 해당 시험이 FAIL 하는지 확인했다.
`strip` 하나는 위 §③ 별도 문단의 이유로 되돌려도 안 죽는다 — 잠금용으로 남겼다.

## 5. 함께 고친 것 (그쪽 점검이 촉발했다)

- **덱 왕복 개행 경고** — 플랫폼이 잡마다 입력/산출 덱의 개행을 대조해 잡 기록과 화면에
  경고를 남긴다. ⚠ 판정 대조만으로는 **혼재 덱을 놓친다**(`count(CRLF)*2 > count(LF)` 규약 때문에
  `implicit` 의 CRLF 86 / LF 15 도 "crlf" 로 보고된다). 그래서 혼재 자체를 규칙으로 본다.
- **ID 발행이 `*INCLUDE` 를 못 봤다고 말한다** — 번호는 그대로다. 발행자 27곳 중 18곳이
  `ModelAssembler::loadBaseModel` 하나를 지나므로 창구 2개로 덮었다. `cclip` 은 인클루드 한
  단계를 실제로 읽으므로 문구가 다르고, **못 연 인클루드**를 예전엔 조용히 넘기던 것도 고쳤다.
- **게시 관문** — 컨테이너에서 못 도는 바이너리를 내보내지 않는다.
  ⚠ 상한은 **2.35** 다. 실사용 소비자 실측 — `SmartTwinPreprocessor.sif` **2.35** ·
  `cli.sif` 2.36 · `api/mcp.sif` 2.41. 최솟값을 택했다. 2.36 을 요구하는 바이너리는 `cli.sif`
  에서는 돌지만 REMAP 체인에서 죽는다.
- **`/api/health` 가 리비전을 말한다** — `revision`·`binary_sha256`·`binary_mtime_utc`.
  기록과 실물이 어긋나면 `revision_matches_binary: false` 로 그 사실을 함께 낸다.
- **게시본을 올렸다** — `dist-20260925-040105Z`(소스 `fb46468`). 09-21 게시본 `cb4e208` 에서
  **26커밋 전진**했다(`git rev-list --count cb4e208..fb46468`).
  09-24~25 의 덱 계약 수정 12곳과 `meshfix` 요소 소실 수정이 이제 REMAP 체인에 도착한다.
- **DB 백업** — 크론에 걸었다(매일 04:10). 그 전까지 **한 번도 돈 적이 없었다.**

## 7. 이 문서에서 일부러 안 쓴 것

- **변이 시험 총계** — 커밋별 수만 근거가 있다(`afbc154` 9/9 · `0704b79` 4/4 ·

  **확인 불가**다(되묻는 것 4번).
- **예약 대역 실제 값** — 그쪽도 갖고 있지 않다고 했고 우리도 없다. 비워 둔다.
