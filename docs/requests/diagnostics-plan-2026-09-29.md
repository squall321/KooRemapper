# DynaForge 진단 체계 — 계획 (2026-09-29)

## 무엇을 만드는가

실패했을 때 **사용자가 버튼 하나로 진단 정보를 넘기면, 우리가 그것만 보고 고칠 수 있게** 한다.
사용자는 서버 셸이 없고 우리는 사용자 화면이 없다. 그 사이를 잇는 것이 이 일의 전부다.

성공 기준은 하나다 — **재현 없이 고칠 수 있는가.** 번들을 열었을 때 "어느 빌드가 · 어떤 덱에 ·
어떤 argv 로 · 무엇을 출력하고 · 어디서 멈췄는지" 가 다 있어야 한다. 하나라도 빠지면 우리는
사용자에게 되묻게 되고, 그 왕복이 이 체계가 없애려는 비용이다.

## 이미 있는 것 (실측 2026-09-29)

기록 토대는 이미 상당하다. 이 일은 "기록부터 시작" 이 아니라 **"흩어진 것을 한 덩어리로 묶기"** 다.

| 있는 것 | 위치 |
|---|---|
| 잡마다 stdout·stderr 를 파일로 보관 | `app/worker/runner_loop.py:337-338` → `Job.stdout_path`/`stderr_path` |
| 실제 실행한 argv + 생성된 yaml | `Job.resolved_cmd` (JSONB, `app/models.py:224`) |
| `exit_code` · `error_summary` · `warnings` | `app/models.py:229-237` |
| 로그 평문 엔드포인트 (경로 봉쇄 포함) | `GET /jobs/{job_id}/logs?which=stdout\|stderr\|both` (`routes.py:208`) |
| 빌드 정체 계산기 | `app/shared/buildinfo.py` — 지금은 `/api/health` 에서만 쓴다 |
| 프런트 다운로드·복사 선례 | `endpoints.ts:106` (Blob) · `TokensPage.tsx:14` (clipboard) |
| API 인스턴스 로그가 남고 일별 회전된다 | `~/.apptainer/instances/logs/<host>/<user>/koorm_api.{out,err}` |

## 없는 것 — 이게 고칠 목록이다

1. **잡마다 어느 바이너리로 돌았는지가 안 남는다.** `buildinfo` 는 `/api/health` 전용이다.
   이 캠페인에서 배포 자리 바이너리가 **다섯 번** 다른 것으로 덮였다. 사흘 전 로그를 받아도
   "그때 어느 빌드였나" 를 답할 수 없으면 그 로그는 증거가 아니다.
2. **로그 줄에 시각이 없다.** `logging.basicConfig(level=INFO)` 뿐이고(`main.py:24`) uvicorn 기본
   접근 포맷도 시각을 안 찍는다. "14:30 에 실패했다" 를 로그와 맞출 방법이 없다.
3. **상관자가 없다.** 사용자가 본 에러와 서버 로그 줄을 잇는 id 가 없다.
4. **접근 로그가 심장박동으로 덮여 있다.** `koorm_api.out` 의 `/api/health` 줄이 1,461개다 —
   감독자가 분당 폴링한다. 감독자 로그가 59% 심장박동이던 것과 같은 병이다(P1-10 ②).
   → ⚠ **정정(정독 실측).** 앱·워커 줄은 stderr 로 가서 `koorm_api.err` 에 따로 쌓인다
     (`grep -c koorm.worker koorm_api.out` = 0). 그래서 이 소음은 **요청 갈래**를 못 읽게 만들고
     **잡 갈래는 막지 않는다.** 처음 판에서 이것을 "번들 품질의 전제" 로 적었는데 과장이었다.
     상관자로 요청을 되짚을 때 필요한 것이지, 잡 진단의 전제는 아니다.
5. **한 덩어리로 내보내는 자리가 없다.** 사용자가 여러 화면을 돌며 긁어 모아야 한다.
6. **잡이 흔적 없이 사라지는 부류가 있다.** 실사용 로그에 `ERROR:koorm.worker:job … crashed` 가
   4건 있고 끝이 `sqlalchemy.orm.exc.StaleDataError: UPDATE statement on table 'jobs' expected to
   update 1 row(s); 0 were matched.` 다 — 잡이 도는 중에 그 행이 사라졌다(세션 삭제 +
   `ON DELETE CASCADE`). 복구 경로(`runner_loop.py:536-542`)가 `j = await db.get(Job, jid)` 뒤
   `if j and j.status == "running"` 이라, **행이 없으면 아무것도 쓰지 않는다.**
   → 실측 확인 — 그 4건은 DB 에 **한 건도 없고**, `error_summary = 'worker exception'` 인 잡은
     전체에서 **0건**이다(현재 잡 11건: succeeded 8 · failed 3). 복구 경로가 한 번도 성공한 적이
     없다. `grep -rn StaleDataError app/` 도 0건이다.

## 정한 것 (사용자 결정 2026-09-29)

| 질문 | 결정 |
|---|---|
| 받는 형태 | **둘 다** — 짧은 요약은 클립보드 복사, 전문은 `.zip` 다운로드 |
| 덱 본문 | **메타만 기본 + 문제 줄은 선택적 opt-in** — 고객 CAE 모델이므로 형상·물성은 기본 제외 |
| 서버측 로그 | **상관자 방식** — 번들에는 correlation id 와 그 id 가 붙은 줄만. 타 사용자 줄은 섞지 않는다 |

## 설계

### A. 기록 — 잡에 환경을 붙인다

`Job` 에 `env_snapshot` JSONB **한 칸**을 더한다. 잡 시작 시 한 번 쓴다.

```json
{ "binary":  {"sha256": "", "md5": "", "revision": "", "glibc_max": "", "mtime_utc": "", "build_method": ""},
  "gmsh":    {"available": true, "version": ""},
  "platform":{"app_env": "", "api_revision": ""},
  "host":    {"nodename": ""} }
```

`buildinfo` 와 `gmsh_probe` 가 이미 이 값을 낸다 — 새로 계산하지 않고 그대로 쓴다. 칸을 여러 개
쪼개지 않는 이유는, 이 값들이 **함께 읽힐 때만** 뜻이 있고 개별 질의 대상이 아니기 때문이다.

**⚠ 번들은 DB 행에만 의존할 수 없다.** 위 6번 때문이다 — 잡 행은 도는 중에 사라질 수 있다.
그러면 남는 것은 디스크의 stdout·stderr 파일과 로그 줄뿐이다. 그래서 두 가지를 같이 한다.

1. 크래시 기록을 **행이 없어도 남는 자리**에 쓴다. `StaleDataError` 를 그 자리에서 잡아 "도는 중에
   잡 행이 지워졌다" 로 해석한다.
   → ⚠ **정정(구현 중 실측).** 처음에 "잡의 stderr 파일에 적는다 — 파일은 세션 삭제와 별개로
     남는다" 고 적었는데 **틀렸다.** `delete_session` 이 세션 폴더를 `shutil.rmtree` 로 통째로
     없앤다(`sessions/services.py:287-289`). 그러면 `open(path,"a")` 가 `FileNotFoundError` 로
     실패해서 정작 이 부류에서 파일에는 아무것도 남지 않는다(손으로 재현했다). **인스턴스 로그가
     정본**이고 파일은 보조다 — 세션이 살아 있는 크래시에서는 잡 옆에 남는 편이 낫다.
2. 번들 조립은 **잡 id + 파일**만으로도 동작해야 한다. 행이 있으면 더 풍부해지고, 없으면 파일과
   로그 줄로 최소 번들을 만든다. 행이 없을 때 404 로 끝내면 정작 가장 진단이 필요한 부류에서
   진단이 불가능해진다.

### B. 상관자 — 사용자가 본 것과 서버 줄을 잇는다

1. 로그 포맷에 **시각과 상관자**를 넣는다. contextvar 를 읽는 `logging.Filter` 로 하고, 없으면 `-`.
2. 미들웨어가 `X-Request-Id` 를 받으면 그대로 쓰고 없으면 만든다. 응답 헤더와 에러 본문에 싣는다
   (`app/shared/errors.py` 에 이미 에러 봉투가 있다).
3. 워커는 잡 구간에서 상관자를 **job id** 로 둔다. 잡 기록과 로그 줄이 같은 문자열로 만난다.
4. `/api/health` 접근 로그를 접는다. 이것은 미용이 아니라 **번들 품질의 전제**다.

### C. 번들 — 내보내는 자리

- `GET /jobs/{job_id}/diagnostics` → JSON. `?deck_lines=1` 이면 문제 줄 전후 몇 줄을 더한다.
- `GET /jobs/{job_id}/diagnostics.zip` → `diagnostic.json` · `stdout.log` · `stderr.log` ·
  `resolved_cmd.yaml` · `server.log`(상관자 일치 줄만).
- 레다ct — 절대 경로는 `<storage>/…` 로 접고, 이메일·토큰은 지우고, 타 사용자 줄은 넣지 않는다.
- 권한은 기존 잡 소유권 검사를 그대로 쓴다. 새 권한 개념을 만들지 않는다.

### D. 화면

실패한 잡 자리에 `[진단 정보 복사]` `[진단 파일 받기]` 두 버튼. 기존 선례를 그대로 따르고
새 UI 양식을 만들지 않는다.

## 하지 않는 것

- 로그 수집 서비스(ELK·Loki 류)를 붙이지 않는다. 폐쇄망 운영이고, 이 문제는 파일 한 덩어리로 풀린다.
- 구조화 로깅 전면 교체를 하지 않는다. 시각과 상관자만 더한다.
- 새 권한·새 역할을 만들지 않는다.
- 덱 원본을 번들에 담는 경로를 만들지 않는다. 필요하면 사용자가 파일을 따로 보내는 것이 맞다.

## 검증

각 단계의 확인 방법을 미리 못 박는다. "동작하게 만들기" 는 기준이 아니다.

1. `env_snapshot` → 잡 하나 돌린 뒤 그 칸에서 `binary.sha256` 이 `/api/health` 의 것과 같다.
2. 상관자 → 일부러 실패시킨 요청의 응답 헤더 id 로 `koorm_api.out` 을 grep 해 줄이 나온다.
3. 번들 → 시험이 단언한다. 비밀 없음 · 타 사용자 줄 없음 · 절대 경로 없음 ·
   opt-in 없이는 덱 줄 없음 · 남의 잡은 403.
4. 회귀 전체(57/57 · ctest · backend)가 초록이고 **덱 바이트 42 op 불변**이다 — 이 일은 덱 편집
   경로를 건드리지 않으므로 산출물이 바뀌면 그 자체가 결함이다.


## 착수 뒤 남은 것 — 근본 원인

이 일은 **관측**을 고쳤다. 원인은 그대로다 — `delete_session`(`sessions/services.py:285-291`) 이
**도는 잡을 보지 않는다.** `shutil.rmtree` 로 세션 폴더를 없애고 행을 지우면 `ON DELETE CASCADE` 가
잡 행을 끌고 간다. 그래서 잡은 여전히 터진다. 달라진 것은 **그 사실이 로그에 남는다**는 것뿐이다.

고치는 방법은 둘이고 **제품 동작이 달라지므로 우리가 정할 일이 아니다.**

1. 도는 잡이 있으면 세션 삭제를 **막는다**(409). 사용자가 먼저 취소해야 한다.
2. 삭제 시 도는 잡을 **먼저 취소**하고(`request_cancel`) 끝난 뒤 지운다. 사용자 눈에는 그대로 지워진다.
