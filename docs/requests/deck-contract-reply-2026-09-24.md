**보내는 쪽**: DynaForge / KooRemapper
**받는 쪽**: LS-DYNA 낙하해석 캠페인 운영
**대상 문서**: `deck-contract-request-2026-09-24.md`
**작성일**: 2026-09-24
**한 줄**: 결론은 맞습니다. **기전 진단은 여러 곳이 틀렸고**, 그대로 착수했으면 한 바이트도 못 고쳤을 자리가 있습니다. 1차로 9건을 고쳤고, 그중 셋은 요청서에 없던 것입니다.

## 0. 먼저 — 요청서를 그대로 믿지 않았습니다

받자마자 착수하지 않고 **8개 항목을 병렬로 실측 검증**했습니다. 요청서가 "이번 문서도 틀린 곳이 있으면 알려 달라"고 적어 주신 대로입니다. 결과가 중요합니다.

- 결손의 실체는 "계약이 없다"가 아니라 **"계약이 한두 op 안에만 있고 공용이 아니다"** 였습니다.
- `strip` 은 이미 LF·CRLF 양쪽에서 바이트를 보존하고 있었고, `restack`·`refine` 은 이미 파트별 요소 수를 왕복 대조해 어긋나면 파일을 안 씁니다. 0에서 시작하는 일이 아니었습니다.
- 대신 **요청서가 못 짚은 더 나쁜 것**이 나왔습니다(§2).

## 1. 요청서에서 사실과 달랐던 것

### 1.1 치명 — 그대로 고치면 한 바이트도 안 고쳐집니다

**① CRLF 소실 기전 오진.** 요청서는 `KFileWriter.cpp:111,229` 의 `std::ofstream out(filename)` 이 "텍스트 모드"라 변환한다고 지목했습니다.

**리눅스 glibc 에서 텍스트 모드 ofstream 은 개행을 변환하지 않습니다.** 실증했습니다 —

```cpp
std::ofstream o("tm.out"); o << "a\r\n" << "b\n";
$ od -c tm.out →  a  \r  \n   b  \n
```

진짜 원인은 **리더가 `line.pop_back()` 으로 CR 을 떼고 그 사실을 기억하지 않는 것**이고, `src` 전체 **78곳**에 흩어져 있습니다. 그리고 CRLF 를 잃은 op(`indent`)의 라이터는 지목하신 파일이 **아니며 이미 `std::ios::binary`** 입니다.

반증 하나 더 — 똑같이 텍스트 모드인 `strip.cpp:177` 이 CRLF 를 **보존**합니다.

> **다만 지목이 완전히 헛것은 아닙니다.** MSVC 빌드가 살아 있고(`scripts/build_windows.bat`), MSVC 텍스트 모드는 `\n` → `\r\n` 을 합니다. CR 을 살려 넘기는 경로는 윈도우에서 `\r\r\n` 을 뱉습니다. **리눅스 CRLF 소실과 원인이 다른 별개 결함**이고, 둘을 한 항목으로 묶으신 것이 실수입니다. 이번에 같이 막았습니다(모든 덱 쓰기를 바이너리 모드로).

**② "DF-20/21 없다"는 틀렸습니다.** DF-20 ⑥(요소 수 증감)은 **이미 완전히 구현돼 있습니다** — `ModelAssembler.cpp:5483-5616`, 파트별 + 합계, 관대 재독과 엄격 재독 2중 대조, 어긋나면 **파일을 안 쓰고 rc=1**. 2026-09-18 에 들어갔고 회귀도 있습니다. 요청서대로 읽고 신규 구현하면 **있는 것을 두 번 짓습니다.** 실제 결손은 ①②③④ 와 발화 범위입니다.

**③ "DF-06 검사가 없다"는 과장입니다.** `scanDeadReferences` 가 해당 키워드를 실제로 훑고 회귀도 통과합니다. 정확한 서술은 **"이번 op 이 지운 ID 만 보는 델타 검사이고 절대 검사가 없다"** 입니다.

이 구분이 결정적입니다 — **요청서의 근거인 TN4 가 정확히 후자이고, 델타 스캐너를 아무리 키워도 TN4 는 안 잡힙니다.** 지운 것이 없으면 함수 머리에서 그냥 돌아갑니다. 이번에 절대 검사를 따로 만들었습니다(§2).

### 1.2 재현되지 않은 주장 — 근거로 쓸 수 없습니다

| 요청서 | 실측 |
|---|---|
| 7자리 EID `9900061` → `99000` 잘림 | **재현 안 됨.** 7자리는 8칸에 들어갑니다. NID/EID 를 9900001~9900363 으로 올려 왕복시켜도 전부 보존됩니다. 리포에 `setw(5)`/`%5d` 는 0건입니다. 실제 경계는 **9자리**입니다 |
| `*KEYWORD` 의 `I10=Y LONG=S` 가 왕복에서 소실 | **재현 안 됨.** indent 왕복에서 보존됩니다 |
| `_ID` 를 놓쳐 TIED 225개를 **0개로 오판** | **재현 안 됨.** `_ID`/`_OFFSET_ID`/`_ID_OFFSET`/`_ID_MPP` 4종 전부 225개로 셉니다. 개수는 키워드 줄만 보므로 0 이 될 경로 자체가 없습니다 |

셋 다 **그쪽 손스크립트에서 난 사고로 보입니다.** 도구 결손의 근거로는 쓸 수 없지만, 손스크립트를 고치실 때 참고가 되실 것 같아 적습니다.

> 특히 `_ID` 건은 **증상 진단이 반대**였습니다. 개수는 멀쩡했고, 진짜 문제는 **쓰기**였습니다(§2-③).

### 1.3 사실 오류

- `ElementCardLayout::optValue("I10")` 라는 API 는 **없습니다.** `ElementCardLayout` 은 클래스가 아니라 자유함수 헤더이고, `optValue` 는 `keywordCardDeckWidth` 내부의 지역 람다입니다. 밖에서 부를 수 없으니 "이미 있는 부품"으로 세시면 안 됩니다.
- `realFieldWidth(intFw)` 는 ID 폭 표가 아닙니다. `intFw>=20 ? 20 : 16` — 정수 칸 폭에 대응하는 **좌표 칸 폭**입니다.
- §2 표의 "요소 카드에 국한된다"가 `*NODE` 를 빠뜨렸습니다. 실제 커버리지는 `*NODE` + `*ELEMENT_*` 입니다(§3.1 본문은 제대로 적으셨습니다).
- DF-04 의 "`ModelAssembler.cpp:4955` 가 각자 처리"는 틀렸습니다. 그 자리의 `TEN NODE` 검사는 카드 경계 판정이 아니라 섹션 배치 힌트이고, 실제 판정(`ecBuildIndex`)은 **요청보다 세밀하게 요소 카드 줄마다** 합니다.
- DF-07 의 "`max+1` 금지" 전제가 과장입니다. `restack` 은 이미 `layers[].pid`/`pid_start` 로 대역을 옮기고 충돌이면 rc=1 로 멈추며, `cnrb2spring` 은 예약 대역 + 8 네임스페이스 exact-match 재검사를 갖고 있습니다. 결손은 "대역 개념이 없다"가 아니라 **"그것이 두 op 안에만 있다"** 입니다.

## 2. 요청서가 못 짚은 것 — 이쪽이 더 나빴습니다

검증 중에 **재현으로** 찾았습니다. 셋 다 고쳤습니다.

### ① `dt2ms` 의 음수 부호가 조용히 사라지고 있었습니다 ★

`*CONTROL_TIMESTEP` 을 쓰는 포매터가 10칸을 넘치면 **앞을 버렸습니다**.

```
dt2ms: -1.0e-7  →  "%10.4E"  →  "-1.0000E-07" (11자)  →  앞이 잘려  "1.0000E-07"
```

실제 출력:

```
*CONTROL_TIMESTEP
       0.0      0.90         0       0.01.0000E-07         0         0         0
                                          ^^^^^^^^^^ 양수입니다
```

**음수는 선택적 질량스케일링, 양수는 고정 dt 스케일링입니다.** 부호 하나로 해석의 물리가 뒤바뀌는데 rc=0·경고 0 이었고, 노드·요소·파트 카운트는 전부 정상이라 알아볼 방법이 없었습니다. 그리고 **저희 매뉴얼이 스스로 `dt2ms: -1.0e-7 # 음수` 를 안내합니다** — 문서를 따른 사용자가 정확히 이 함정을 밟습니다.

요청서 DF-03 의 "넘치면 자르지 말고 raise" 는 **맞는 요구인데 고칠 자리가 요소 ID 가 아니라 `*CONTROL` 값 쪽**이었습니다.

### ② `contact modify` 가 SSID 칸을 덮어쓰고 있었습니다 ★

`_ID` 옵션은 `cid + 제목` 줄을 Card 1 앞에 둡니다. **읽기는 그것을 세고 있었지만** 판정이 지역 변수라 `ContactDef` 에 안 남았고, **편집 5곳이 `hasTitle` 만 봤습니다.**

```
원본     '         1         2         3         3'   ssid=1 msid=2
modify   '      0.33         2         3         3'   ← ssid 칸에 마찰계수
```

슬레이브 파트 참조가 파괴되고, 정작 FS 는 `0.2` 그대로인데 도구는 `Modified: FS=0.330000` 이라고 **성공을 보고합니다**. `modify soft:2` 는 **필수 Card 3 를 없앱니다**.

**접촉 개수는 멀쩡합니다.** 요청서가 "구조 카운트만으로 통과시키지 마라"고 하신 바로 그 사례이고, 요청서 자신이 `_TITLE` 만 쓰는 예제로 보셔서 놓치신 자리입니다.

### ③ `*DATABASE_HISTORY_*_SET` 의 세트 ID 를 요소 번호로 읽고 있었습니다

EID 축 스캐너가 `_SET` 변형을 함께 걸어, 세트 ID 와 같은 번호의 요소가 지워지면 **"지워진 요소" 오탐 + rc=1** 이 났습니다. 바로 위 PID 축에는 같은 제외가 처음부터 있었습니다 — 한쪽만 빠져 있었습니다.

### 3.1 개행 — 한 곳이 아니라 19개 op 이 깨져 있었습니다

전 op 매트릭스를 만들어 재니 **16개가 깨져** 있었습니다. 두 형태였습니다.

| 형태 | op |
|---|---|
| 전멸(CRLF 0) | `indent` `database` `cnrb2solid` `cnrb2spring` `ale` `iga` `map` `shellmap` `unfold` `extract-surface` `tetremesh` `battery` … |
| **혼재** | `prestress` `relax` `merge` `contact` |

**혼재가 더 나쁩니다** — 한 파일 안에서 개행이 갈립니다. `prestress` 가 교과서적이었습니다. 원본 줄은 CR 을 안 뗀 채 `"\n"` 을 붙여 CRLF 가 되는데, 새로 끼우는 `*INCLUDE` 두 줄만 LF 였습니다.

**78곳을 고치지 않았습니다.** 읽을 때 CR 을 떼는 것 **자체는 옳습니다** — 줄 끝에 `\r` 이 남으면 `stoi`·`substr` 뒤의 공백 판정·`back()` 분기가 전부 오동작합니다. 가장 유혹적인 최소 수정(`pop_back()` 삭제)이 제일 위험합니다. 없던 것은 **뗀 개행을 쓸 때 되붙이는 것**이라, 공용 쓰기 계층(`DeckWriter`)을 만들어 거기로 모았습니다.

요청서의 mmap 우려도 반영했습니다 — 문자열로 모아 치환하지 않고 **스트리밍**으로 바꿉니다(상수 메모리).

### 3.2 절대 참조 검사 — 강건성이 절반입니다

없는 세트를 가리키는 카드 5종을 심은 덱이 `[OK] Mesh is valid` · rc=0 으로 통과하던 것을 잡습니다. 다만 **오탐을 한 번 내면 사람은 이 보고를 통째로 무시하고, 그러면 진짜를 놓칩니다.** 그래서:

- **칸 뜻이 확실한 카드만** 봅니다. CONTACT 는 SSTYP/MSTYP 가 세트라고 **말할 때만**(0·2·4) 보고, 타입 칸이 비었거나 3(파트 ID)이면 손대지 않습니다. 검사 안 한 자리는 **세어서 알립니다**.
- `*PARAMETER` 의 `&name` 줄은 값이 기호라 건너뜁니다.
- `_GENERATE`/`_ADD`/`_TITLE`/`_ID` 의 줄 구조를 반영합니다.
- ⚠ **`*INCLUDE` 가 있으면 단정하지 않습니다.** 세트가 그 안에 정의됐을 수 있으므로 경고로 낮추고 "이 덱에서 못 찾았다"로 말하며 어느 INCLUDE 를 안 봤는지 적습니다. (첫 구현은 여기서 단정해 오탐을 냈고, 시험으로 잡아 고쳤습니다)
- 저장소 예제 덱 40~60개에서 **오탐 0건** 확인.

`info` 의 **rc 는 그대로 0** 입니다 — 플랫폼 워커·pyKooCAE 체인이 그것을 기대합니다. 제출 차단은 별도 preflight 의 몫으로 남깁니다.

## 5. 저희가 막힌 것 — 답을 주셔야 진행됩니다

**① DF-07 예약 대역의 실제 값.** 요청서의 `500323`·`9000001` 을 리포 전체에서 찾으면 유일한 히트가 **요청서 자신**입니다. 관례가 있다는 것은 확인했지만 **값을 모르면 골격만 만들고 비워 둘 수밖에** 없습니다. 하위 전처리기(KMM 등)가 쓰는 대역 목록을 표로 주십시오 — 어느 도구가 어느 구간을 점유하는지.

**② DF-08 의 "템플릿"이 무엇입니까.** "원본/템플릿/per-run 3자 대조" 중 가운데가 비어 있습니다. 지금 이 리포의 template 은 리포트용 파일명 매칭이라 기준 재고와 무관합니다. 캠페인에서 "템플릿"이 가리키는 실체(파일? 덱? 파트별 기대 재고표?)를 알려 주십시오.

**③ 회귀 코퍼스.** §부록 B 에 주신다고 하신 운영 덱(6face 19개 + A27·M1/M3·TN·Cross)을 받으면 SYS-02 를 그 위에서 돌리겠습니다. 지금 매트릭스는 저장소 예제로만 돕니다 — **2줄 포맷 혼재, `I10=Y LONG=S`, `_ID` 접미사 TIED 가 든 실 덱**이 특히 필요합니다.

**④ 동작 변경 합의 하나.** 현재 dangling 보고(`pid_refs: strict`)는 **rc=1 인데 덱은 디스크에 나갑니다.** 요소 수 대조는 반대로 파일을 안 씁니다. 두 관문의 결말이 다른데, 통일하는 것은 동작 변경이라 합의가 필요합니다. 어느 쪽이 맞습니까 — "덱은 쓰되 믿지 말라" 인지 "아예 안 쓴다" 인지.

## 6. 확인 부탁드립니다

- **`relax`·`strip` 의 출력 바이트가 달라집니다.** 이 둘은 CR 을 안 떼서 지금까지 CRLF 를 통과시켰습니다. 통일하면 `relax` 의 혼재 출력이 전부 CRLF 로 바뀝니다 — **의도한 개선이지만 기존 산출물과 바이트가 달라집니다.** 하류에서 diff 로 검증하시는 파이프라인이 있으면 한 번 크게 흔들립니다.
- **`contact modify` 의 결과가 달라집니다.** 지금까지 `_ID` 카드에 `modify` 를 거신 적이 있다면 **그 덱의 SSID 가 망가져 있습니다.** 해당 캠페인이 있으면 알려 주십시오 — 어느 범위가 영향인지 같이 보겠습니다.
- 위 §1.2 의 재현 실패 셋은 **그쪽 손스크립트 쪽을 보셔야 할 것 같습니다.**

틀린 곳이 있으면 알려 주십시오. 이번 검증도 저희 판단이고, 한 번은 저희가 `*INCLUDE` 단정으로 오탐을 냈다가 시험으로 잡았습니다.
