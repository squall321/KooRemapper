# SP 허브 코어 API 개통 요청서 — DynaForge 가 과제 기준정보를 받으려면

**보내는 쪽**: DynaForge — `KooRemapper/platform` (`971f3ab` 기준)
**받는 쪽**: **StandardPlatform 허브를 운영하는 쪽** (어느 인스턴스인지 저희가 모릅니다 — §1)
**작성일**: 2026-10-14
**한 줄**: DynaForge 에 과제·개정 기능을 넣었습니다(S0~S7 끝, 시험 536 녹색). 켜려면 **허브 쪽에서
셋**이 필요합니다 — 어느 인스턴스인지 · 타입 넷의 `core` 를 켜기 · `core:read` 범위 토큰 하나.
**성격**: 요청 셋(§1~§3)과 확인 하나(§4), 나머지는 알림입니다.
**근거**: 전부 `StandardPlatform@f7485c0`(submodule `external/StandardPlatform`)을 읽은 것입니다.
읽기만 했고 그 리포의 URL 에 접속하지 않았습니다.

## 0. "허브 설정" 이 무엇인가 — 저희가 쓰는 말의 뜻

DynaForge 의 `.env` 에 들어가는 **두 줄**입니다.

```
KOORM_SP_CORE_URL=https://<허브>/api      ← §1
KOORM_SP_CORE_TOKEN=<core:read 토큰>      ← §3
```

둘 다 **바깥이 정해 주는 값**이라 앱이 스스로 알 수 없습니다. 그래서 요청으로 올립니다.
두 줄이 들어오면 DynaForge 는 기능을 **스스로 켭니다**(옵션을 안 건드리면 있는 것으로 정합니다).
들어오기 전에는 기능이 화면에서 **안 보이고** `/api/v1/ontology/*` 도 409 와 사유로 거절합니다.

## 1. 🔴 허브가 어느 인스턴스입니까

이 틀로 선 플랫폼이 다섯입니다(`docs/새-플랫폼-만들기.md` §3.6) — MatNexus(8010/11/12) ·
TestScope(8020/21/22) · StandardPlatform(8040/41/42) · AutoJigGenerator(8060~) ·
SimEngBay(8070~). 그중 **PLM 기준정보를 받아 두고 내려 주는 쪽**이 허브입니다
(`ontology/managed.py` 머리말: "PLM 기준정보는 허브 플랫폼이 원천(PLM)에서 받아 쌍둥이
플랫폼에 내려준다").

저희가 모르는 것 —

- 어느 인스턴스가 허브입니까. (아직 없으면 "아직 없다" 가 답입니다 — 그러면 §2·§3 도 뒤로 갑니다.)
- 코어 API 의 **주소**는 무엇입니까. 저희가 넣는 값은 `/api/core` 의 **한 단 위**입니다 —
  예 `https://hub.example/api`(저희 클라이언트가 `/core` 를 붙입니다).
- 저희 박스(DynaForge, cae00)에서 그 주소에 **닿습니까**. 터널이 필요하면 그것도 알려 주십시오.

> 이 개발 박스에서는 8010~8072 중 열린 것이 `8013` 하나인데 컨테이너의 MCP 서버
> (`cwd=/mcp-server`)이고 게이트웨이 설정에도 없습니다. **운영은 저희가 못 봅니다.**

## 2. 🔴 타입 넷의 `core` 를 켜 주십시오

`ObjectType.core`(`ontology/models.py:248`)가 **바깥에 여는 스위치**입니다 —
*"켜면 `/api/core` 로 나간다 … 켜면 계약이 된다 — 이 타입의 slug 와 속성 key 가 남의 시스템
코드에 박힌다."*

필요한 타입 넷입니다(`pipeline/core/plm-core.json` 그대로) —

| slug | 라벨 | 저희가 쓰는 것 |
|---|---|---|
| `plm_task` | 과제 | **key = 과제코드**(정체성) · label = 과제명 · `project` · `task_status` |
| `plm_model` | 개발모델 | `task` · `model_revision`·`model_revision_kind`(개정 후보의 근거 ③) |
| `plm_project` | 프로젝트 | `plm_task.project` 가 가리키는 쪽 |
| `plm_test_site` | 시험 주체 | 과제 속성 `test_site` 가 가리키는 쪽 |

★**`plm_task` 하나만 열려도 시작할 수 있습니다.** 나머지는 과제의 참조 칸이 가리키는 쪽이라,
안 열리면 그 칸이 **키 문자열로만** 보입니다(저희는 그 값을 그대로 저장합니다 — 수신 규칙 10).
급하면 `plm_task` 부터 열어 주십시오.

⚠ **켜면 계약**이라고 적혀 있어서 드리는 말씀 — 저희는 slug 와 속성 key 를 코드에 박지
**않습니다.** 카탈로그가 주는 것을 그대로 담고(`properties` JSONB), 모르는 칸은 무시합니다
(수신 규칙 5). 그래서 칸이 늘어도 저희가 안 깨집니다. 다만 **`plm_task` 의 slug 와
`key`(과제코드)** 는 정체성이라 바뀌면 영향이 있습니다 — 바꾸실 때 `renamed_from` 으로
보내 주시면 저희가 키를 옮깁니다(§6 참고).

## 3. 🔴 `core:read` 범위 토큰 하나

`CORE_SCOPE = "core:read"`(`coreapi/services.py:81`)이고 `app/shared/scopes.py` 에 등록된
**좁은 읽기 범위**입니다. `consumers()`(`:169`)가 그 범위를 가진 PAT 를 소비자로 보여 주고,
`core:read` **만** 가진 토큰은 `narrow=True` 로 표시됩니다(`:207`).

부탁 —

- **`core:read` 만** 주십시오(`read` 를 겹쳐 주지 마십시오). 넓은 토큰은 사고의 크기를 키웁니다.
  그 리포의 지침서는 *"받아만 가면 `read` 로 충분하다"*(`docs/외부-시스템-연동-지침서.md` 797행)
  라고 적었는데, **`core:read` 는 그보다 더 좁습니다** — 코어 API 만 읽습니다. 그쪽을 주십시오.
- 토큰 **주인이 누구인지**가 뜻을 가집니다. 소비자 목록에 "DynaForge" 로 보이도록 발급해
  주시면, 나중에 타입을 고치실 때 누가 쓰는지 보입니다(타입 편집에 `core_consumers` 가 뜹니다 —
  `ontology/routes.py:759`).
- 저희는 **쓰기 범위가 필요 없습니다.** 받기만 합니다(§6).

## 4. 담당·참여 관계도 함께 열립니까

과제의 담당 부서·담당자·참여는 **칸이 아니라 관계**입니다(`pipeline/core/work-core.json` —
`dept_in_charge`·`responsible`·`participates` 등 10개). 코어 API 는 관계도 줍니다
(`GET /core/{type}/relations`, 카탈로그의 `relations`·`relation_kinds`).

- 그 관계들이 **같이 열립니까**, 아니면 타입만 열립니까.
- 끝점이 부서·계정이면 저희는 **행을 만들지 않고 선만** 저장합니다(SP 의 `object_links` 와
  같은 자리). 저희 소속 정본은 포탈이 HMAC 로 서명해 보내는 `X-Heax-User-Affiliation` 이라
  부서를 복제하지 않습니다 — SP 스스로 §3.6 에 *"부서를 `objects` 에 복제하면 두 벌이 되고
  **반드시 갈린다**"* 고 적은 그 이유 그대로입니다.

## 5. (선택) 정의가 바뀔 때

카탈로그가 `revision` 지문을 줍니다(`CoreCatalogOut.revision`). 저희는 받을 때마다 그 값을
타입별로 저장하고, 바뀌면 보이게 합니다. **알림까지는 필요 없습니다** — 다만 **속성 key 를
지우거나 이름을 바꾸실 때**는 미리 말씀해 주시면 좋겠습니다. 저희가 그 칸으로 화면을 만들지는
않지만, 개정 후보의 근거 ③(`plm_model.model_revision`)은 그 key 를 봅니다.

## 6. 알림 — 우리가 하지 않는 것과 지키는 것

**하지 않는 것** — 과제를 만들거나 고치지 않습니다. DynaForge 에 그 길이 **아예 없습니다**
(라우트 시험이 쓰기 경로의 집합을 못박아, 나중에 누가 과제 `PUT` 을 더하면 회귀가 빨개집니다).
받은 행은 `source="hub"` 로 표시하고 우리 길에서 손대지 않습니다. 우리가 만드는 것은
**개발 개정**(`dev_revision`, key `<과제코드>@<dv1>`) 하나이고, 그것이 `revision_of` 로 과제를
**가리킵니다** — `managed.py` 가 "막지 않는 것" 으로 적은 그 방향입니다.

**지키는 것** — 받는 쪽 **규칙 열하나를 전부** 구현했습니다
(`docs/외부-시스템-연동-지침서.md` §4.2, 311~343행). 회귀 23항이 가짜 허브로 전수 확인합니다 —
`as_of` 를 그대로 되돌리기 · `next` 가 있으면 시계를 **안 옮기기** · `key` 저장 ·
`deleted`/`merged_into`/`hidden` · 모르는 칸 무시 · 같은 행 두 번 · `since` 없을 때 **부재 대조**
(★전량에 0건이 오면 **아무것도 하지 않습니다** — 「다 지워졌다」와 「조회가 잘못됐다」를 가릴
수 없어서입니다) · 되살림 · 합쳐진 쪽의 선 · 참조 칸의 옛 `key` · **404 두 가지**
(`APP-CORE-0001` 이면 그 타입 수신을 **멈추고 알립니다** — 계속 두드리지 않습니다).

★**한 가지는 키트에 없어서 저희가 채웠습니다** — `coreapi/kit/sp_core_pull.py` 는
`renamed_from` 을 **전혀 다루지 않습니다**(`ENVELOPE`(`:43`)에도 없습니다). 그런데 규칙 4 가
요구합니다: *"`renamed_from` 이 있으면 그 옛 식별자로 제가 가진 행을 찾아 키를 옮긴다 —
안 그러면 **같은 것이 둘이 된다**."* 그대로 쓰면 개명 뒤 같은 과제가 둘이 됩니다. 저희는
구현했고 옛 키를 `previous_keys` 에 쌓습니다. **키트를 쓰는 다른 설치에도 같은 구멍이 있습니다** —
알려 두는 것이 맞겠다 싶어 적습니다.

## 7. 받으면 저희가 하는 일 (참고)

1. DynaForge 박스 `platform/.env` 에 두 줄을 넣고 `./infra/scripts/start.sh`
   (마이그레이션까지 같이 돕니다).
2. `POST /api/v1/ontology/sync` 로 **한 번 받아 봅니다.**
3. `GET /api/v1/ontology/sync` 로 타입별 시계·받은 수·카탈로그 판을 확인하고,
   `GET /api/v1/system/capabilities` 의 `ontology.enabled` 가 참인지 봅니다.
4. 결과(받은 타입·건수, 막힌 것이 있으면 그 사유)를 회신드립니다.

포탈에도 이 두 줄을 넣는 설정 항목을 만들어 뒀습니다 —
HWAXPortal `backend/config/setup_requests.yaml` 의 `dynaforge-ontology`(`9f9e667`).
