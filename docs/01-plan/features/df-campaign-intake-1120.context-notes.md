## 2026-11-20 · 소스에서 본 것(설계에 닿는 것만)
- intake 는 리포트를 읽고(크기 상한 · gunzip · 묶음 풀기) → 세션을 만들거나 찾고 → K 파일을 저장하고(커밋) → `ingest_report` 가 해석 ·
  검증을 모두 끝낸 뒤 쓰기 시작한다. 해석 실패(`ValueError`)면 라우트가 방금 만든 세션이나 K 파일을 지우고 400 을 낸다.
- `ingest_report` 의 쓰기 구간은 커밋 하나다(개정 잇기만 저장점). 그래서 쓰기 구간 맨 앞에서 런 행을 잠그면(`FOR UPDATE`) 그 커밋까지 잠금이
  이어진다 — 같은 런의 둘째 요청은 잠금에서 기다렸다가 「이미 가졌다」 를 본다. 잠금을 저장점 밖에서 잡으므로 개정 잇기가 되감겨도 풀리지
  않는다.
- 세션 팩토리는 `expire_on_commit=False` 다. 되감기(rollback)는 객체를 만료시켜 뒤의 정리 코드가 속성을 읽다 깨진다 — 「이미 가졌다」 로 물러날
  때는 되감지 않고(아직 아무것도 안 썼다) 정리 코드의 커밋이 잠금을 푼다.
- 저장된 리포트 파일의 sha256(`SessionFile.sha256`)은 올라온 바이트(푼 뒤)의 sha256 과 같다 — 런의 지문으로 그 값을 쓴다.
- MCP `_unwrap` 은 4xx 에서 `message` 만 올린다. 그래서 같은 이름 캠페인의 409 는 id 를 글에도 넣는다(`data.campaign_id` 는 REST 손님용).
- intake 는 토큰마다 분당 60 호출이다(`ratelimit_upload_per_min` — 넘으면 429 `Retry-After`). 1,393 건이면 한도만으로 23 분쯤이다 — 올리는
  쪽이 429 를 지켜야 한다. `capabilities.intake` 와 업로드 안내에 싣는다.
- `rest_catalog` 은 이 리포 · SP 어디에도 없다(게이트웨이의 것). 우리 쪽의 「한 곳에서 공표」 는 `capabilities.intake` 다.
- 도구 수는 `server.py` 의 `@mcp.tool(` 를 세어 낸다(스모크 · capabilities · parity 시험). 글에 박힌 90 은 README · TOOLS.md ·
  CLAUDE_DESKTOP.md 와 cae00 점검 문서(게시 때 고친다)다.

## 2026-11-20 — 정할 것 3 실측(큰 리포트 파싱 메모리 · 상한은 고르지 않았다)
- 방법 — `scripts/bench_sphere_scale.py build` 로 구면 예제(`koo_sphere_report/examples/Test_001_report.html` · 6.4 MB · 26 각도)를 N 각도로
  늘린 합성 리포트 넷을 만들고, `ingest_report` 의 파싱 구간(바이트 → `decode` → `extract_embedded_data` → `parse_data`)을 크기마다 새
  프로세스로 돌렸다. 구운 `api.sif` 의 python(`-I`) · `prlimit --as` 8 GB 아래 · 올린 바이트(`raw`)는 저장 때까지 살아 있으므로 끝까지 쥔 채로.

| 파일 크기 | 각도 | 글(str) 크기 | 최대 RSS | 크기 대비 | 걸린 시간 |
|---|---|---|---|---|---|
| 47 MB | 207 | 94 MB | 389 MB | 8.2 배 | 0.5 초 |
| 96 MB | 420 | 191 MB | 776 MB | 8.1 배 | 1.2 초 |
| 286 MB | 1,260 | 572 MB | 2,303 MB | 8.0 배 | 3.8 초 |

- 읽기 — 최대 메모리는 파일 크기의 약 8 배로 곧게 는다. 리포트에 한글이 있어 글이 글자마다 2 바이트(파일의 2 배)가 되고, 그 위에 풀린
  JSON 객체가 얹힌다. 꼭대기는 임베드를 푸는 순간이다(글 + 객체가 같이 산다). 10-28 통째 반입 실측(484 MB → 4.0 GB · 8.3 배)과 같은 비율이다.
- 지금 받는 가장 큰 것 — 압축 없이 512 MB(`max_upload_mb`) → 약 4.1 GB. gzip 으로 올리면 풀린 크기 2,048 MB(`max_report_mb`)까지 받으므로
  같은 비율이면 약 16 GB 다(이 크기는 돌리지 않았다 — 비율로 늘린 값). 동시에 오는 올리기는 그 수만큼 곱해진다.
- 재지 않은 것 — 런 하나짜리 리포트(deep 종류)의 실제 크기와 꼴. 위는 구면 리포트를 늘린 대역이다. 저장 뒤 구간(곁파일 · 케이스 행)은
  이번에 따로 재지 않았다(10-28 통째 실측이 파싱 구간과 거의 같았다).
- 고를 수 있는 것(고르지 않았다) — (가) 그대로 둔다 (나) 풀린 크기 상한 `max_report_mb` 를 낮춘다(예 — 512 면 꼭대기 약 4 GB) (다) 파싱을
  한 번에 하나로 줄 세운다(동시 올리기가 곱해지지 않게) (라) 글을 거치지 않고 바이트에서 바로 푼다(파서를 고쳐 2 배분을 던다 — 따로 재야 한다).

## 2026-11-20 · 짓기 — 지으며 고른 것(계획 3 · 4절에도 옮겼다)
- 4xx 를 런에 적는 자리는 intake 의 yield 의존성(`_campaign_run`)이다. 라우트 안 여러 갈래의 `raise HTTPException` 을 하나하나 감싸지 않고,
  FastAPI 가 라우트의 예외를 의존성의 `yield` 자리로 던져 주는 것을 쓴다(0.136 실측). 적기 전에 되감아 잠금 · 반쯤 쓴 것을 놓는다.
- 런에 **적히지 않는** 것 — 401(런을 찾기 전) · 429(분당 한도가 라우트 의존성이라 먼저 돈다) · 요청 꼴 오류 422(`file` 칸이 없는 것 따위 —
  `RequestValidationError` 는 `HTTPException` 이 아니다) · 게이트웨이가 앞에서 막은 요청 · 5xx. 429 · 422 는 시험이
  못박는다(`test_shape_errors_and_the_rate_limit_are_not_recorded`). 「올렸는데 pending 그대로」 면 이 갈래다 — 도구 설명과 업로드 안내에
  적었다.
- 캠페인의 `dev_rev` 는 intake 폼과 같은 검사(`parse_stage` · 8 자)고 `project` 는 64 자다. 틀리면 422 + 까닭 글이다. MCP 는 오류에서 글만
  보므로 뜻 오류는 pydantic 에 맡기지 않고 `HTTPException(422, 글)` 로 낸다.
- `thickness_axis` 는 x · y · z 소문자도 받고 대문자로 둔다.
- 목록 다시 올리기는 **보낸 칸만** 맞춘다(`exclude_unset`). `{"run_key": k}` 만 다시 보내면 doe · pitch · roll 이 그대로고, `"pitch": null` 을
  보내면 비운다. 계획 3절 12 를 이 뜻으로 고쳤다.
- `ingest-status` 의 `limit` 은 기본 200 · 최대 5,000(목록 한 요청의 최대와 같다)이고 런은 올린 차례(id 순)로 온다.
- 색인은 `ix_campaign_runs_report_id` 하나만 더 뒀다(리포트를 지울 때 FK 가 런을 찾는다). 캠페인 안 열쇠 찾기는 유일 제약의 색인을 쓴다.
- 다른 내용 거절(409)의 글은 두 지문을 모두 싣고 「가진 리포트는 그대로 둡니다.」 로 끝난다. 응답 `data` 에 `offered_sha256` 이 있다.
- `capabilities.intake` — 계획은 「`batch` 를 켠다」 였는데 한 호출은 여전히 리포트 하나다. `batch: true` 만 두면 「한 호출에 여럿」 으로 읽힐
  수 있어 `reports_per_call: 1` 을 같이 싣고, `rate_limit_per_min`(한도가 꺼져 있으면 null) · `campaign`(`create` · `manifest` · `status` 길 ·
  `form_fields` · `states`)을 더했다. 이 칸 이름들은 이름표에 없던 것이라 계획 4절에 확인받을 것으로 적었다.
- MCP 의 상수 `CAMPAIGN_STATES` · `CAMPAIGN_RUNS_MAX` 는 백엔드 것의 사본이다 — 계약 시험이 둘을 묶는다(`STATES` · `limit` 의 `le` ·
  `RunsBody.runs` 의 `max_length`). `create_campaign` 의 인자 집합도 `CampaignBody` 의 칸 집합과 같아야 한다(② 단계에서 칸을 더하면 시험이
  빨개진다).
- 파이썬 손님(`platform/clients/python`)에는 캠페인 메서드를 넣지 않았다(이름표에 없다). 콘솔 화면도 없다 — parity 표에 「웹 화면은 아직 없다」
  로 적었다.

## 2026-11-20 · 짓기 — 알고 둔 가장자리
- 있는 세션에 올릴 때 그림 붙이기(`attach_media`)가 `ValueError` 를 내면 400 인데 리포트는 이미 들어가 있다(예전부터의 동작). 캠페인 런이면 런은
  `rejected` 로 읽히면서 `report_id` 를 가진다 — 같은 바이트를 다시 올리면 `skipped` 가 된다.
- 다른 내용으로 거절된 런이 가진 리포트를 뒤에 지우면, 런은 `rejected` 와 옛 까닭을 그대로 보인다(다음 시도가 덮는다). 받았거나 건너뛴 런만
  `pending` 으로 돌아온다(계획 3절 9).
- 5xx 로 끝난 intake 는 예전처럼 세션 찌꺼기를 남길 수 있고 런에는 아무것도 적히지 않는다.
- 건너뛰는 재업로드도 파일 전체를 보낸다(지문은 서버가 잰다). 올리는 쪽이 `campaign_ingest_status` 로 받은 런을 먼저 걸러 내면 보내지 않아도
  된다 — 업로드 안내에 적었다.
- 분당 60 호출은 그 토큰의 올리기 길 일곱(리포트 여섯 · 세션 파일 하나)이 나눠 쓴다 — intake 만의 한도가 아니다.
