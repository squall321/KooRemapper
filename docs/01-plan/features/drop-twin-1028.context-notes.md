# 낙하 트윈 결정 노트 (2026-10-28)

## 1. 제안서의 상당 부분은 이미 있었다 — 그 위에 얹는다
제안서는 S1 리더로 PhysicsNeMo-Curator·PyDPF, 꼴로 Zarr, S2 를 새 화면으로 잡았다. 10-28 에 읽어 보니 이미 있었다.
- **S2** — DynaForge 프런트 `spherePlot`(경위도 히트맵 · 최악 각도) · 각도별·파트별 최대(DB) · lon/lat(swap 반영).
- **S1** — KooD3plotReader `SurfaceExtractor` · `HDF5Writer`(메시 1회 · 타임스텝마다 양자화 + int8 시간 델타 + gzip). 이미 후처리 사슬의 리더다.
- **CAD 쪽** — StepForge `step_material`(STEP 재질 직접 읽기) · `gltf_batch`(정점 `_PARTID`) · `deck_step` · `match_parts_across`.
그래서 리더를 하나로 유지하면 d3plot 호환성 리스크가 사라지고, PyDPF 의 라이선스 문제도 피한다.

## 2. 단면 영상이 느린 까닭은 GPU 하나로 안 풀린다
운영 후처리 `koo_deep_report` 의 기본은 LS-PrePost 백엔드다. 사용자가 「너무 오래 걸려 안 쓰게 된다」고 했고, 코드에서 셋을 확인했다.
① 잡이 곱으로 는다(필드 2 × 축 3 = 각도당 6개, 파트별이면 × 파트 수) ② 잡마다 LS-PrePost 가 같은 d3plot(35~50 GB)을 처음부터 연다 ③ Xvfb 위 CPU 소프트웨어 GL 로 그린다.
남은 기록은 영상 하나 약 34초다(★10-28 실측 — 4,952 상태 덱은 약 100초, 34초는 재현 안 됨 · §19). GPU 는 ③만 고친다. S1 추출본(②)과 온디맨드(①)가 있어야 영상이 쓸 만해진다.
★처음엔 「단면마다 d3plot 을 다시 읽어서」로 단정하려다, 코드에 상태를 공유하는 경로가 있는 것을 보고 멈췄다. 34초를 낸 것은 우리 래스터라이저가 아니라 LS-PrePost 배치였다. 34초의 내역(열기·그리기·인코딩)은 아직 아무도 재지 않았다 — P0 실측 항목이다. [[feedback-dont-invert-diagnosis]]

## 3. 브라우저 뷰어와 Omniverse 를 둘 다 한다 (사용자 10-28)
- 화질은 Omniverse 가 확실히 낫다(사진급). 응력·변형 **정보**는 둘이 같다.
- 사용자 결정 — 둘 다 한다. Omniverse 는 디지털 트윈 보고와 **실물 시험 재현**에 쓴다. 시험 재현은 Omniverse 를 보고 도구에서 **해석 검증 도구**로 바꾸는 쓰임이다.
- 시험 재현이 바탕에 거는 요구 — 시간 해상도(카메라 fps 에 맞춘 해석 출력 주기) · ×1 배율 · 매끈한 CAD(StepForge 대응이 필수가 됨) · 외관 데이터 · 카메라 교정 · 파손 표현.

## 4. 새 포지를 지금 세운다 (사용자 10-28)
처음엔 「렌더 잡으로 시작해 신호가 차면 포지로 올리자」고 권했다. 사용자가 **지금 세운다**로 정했다. 그 권고는 쓰지 않는다.
대신 포지 안에서 얇게 시작한다 — P0 확인 → P1 골격(빈 장면 1장) → P3 배치 mp4 → P4 시험 재현 → P5 스트리밍. 스트리밍이 가장 비싸고 가장 덜 급하다.

## 5. 이름 — SceneForge (사용자가 정해 달라고 함, 확정은 아직)
정본이 장면(USD stage)이라 장면에 붙였다. 렌더러를 바꿔도 이름이 맞는다. 충돌 없음(포털 문서 · HEAXHub integrations).
대안 TwinForge(SmartTwin 계열과 헷갈림) · RenderForge(좁게 읽힘). **리포 생성·HEAX 등록은 확정 뒤** — 이름은 적용 전 확인이라는 기록된 규칙 때문이다. [[feedback-confirm-naming]]

## 6. 서로를 부르지 않는다 — 잇는 것은 포털 절차
10-15 DynaForge·StepForge 합의(파일로만)를 셋으로 넓혔다. 포지 사이를 직접 호출로 이으면 한쪽 장애가 다른 쪽을 멈추고, 누가 정본인지 흐려진다.
사슬은 포털 절차(R2)가 각 포지 도구를 차례로 부르며 id 를 넘긴다. 이렇게 하면 포털 요청서(09-16)가 바라던 「절차가 한 줄도 안 고치는」 꼴과도 맞는다.

## 7. 브라우저 뷰어는 DynaForge 화면에 (D-5 권장)
S2 맵이 DynaForge 에 있으니 각도를 누르면 바로 열리는 자리가 자연스럽다. 입력은 StepForge glb(C-7) · 가중치(C-6) · S1(C-3) 이고, 계약이 같아서 StepForge 뷰어로 옮겨도 된다.

## 8. S1 은 HDF5 를 기본으로 (D-2 권장) — ★10-28 조사: Kit-CAE 3.0 은 HDF5 를 못 읽는다 (§17)
KooD3plotReader 에 이미 있고, 제안서 기준 Kit-CAE 가 HDF5 를 기본으로 받는다(Zarr 는 어댑터가 필요하다고 제안서가 적었다). 다만 Kit-CAE 가 기대하는 HDF5 레이아웃은 P0 에 확인한다.

## 9. 1,000각도 리포트는 약 1 GB 다 — ★10-28 실측으로 고침: 484 MB (§11)
새 판 sphere 리포트가 각도당 약 1 MB 다(10-28 실측). DynaForge 는 상세 질의마다 원본 HTML 을 통째로 다시 파싱하고 캐시가 없다. 맵은 DB 값이라 괜찮지만 각도별 상세는 막힌다. P1 에 반입 블록 분리를 넣었다.

## 10. 요청서는 쓰기만 했다 — 10-28 StepForge 는 보냈다 (§13)
StepForge·포털 요청서는 작성만 했고 보내지 않았다. 다른 팀에 보내는 것은 사용자 승인 뒤다(기록된 규칙).

## 11. 「1 GB」 는 틀렸다 — 484 MB 다 (10-28 실측)
1각도 파일 1.08 MB 를 그대로 1,000배 했었다. 그 안에는 각도와 무관한 고정 템플릿(약 0.35 MB)과 장치 메시가 들어 있고, 각도마다 늘어나는 것은 약 0.49 MB 다.
합성 1,000각도로 쟀다 — 반입 24초 · 4.0 GB, 상세 질의 1회 22초 · 4.0 GB. 22초 중 질의 자체는 0.13초다. 나머지는 원본 재파싱이고, 그중 17초가 파이썬으로 한 글자씩 도는 괄호 맞추기(`_balanced_json`)다.
`json.JSONDecoder().raw_decode` 로 바꾸면 4.5초 · 3.1 GB 다. 그래도 질의마다 GB 단위라 블록 분리(P1)는 그대로 필요하다(API 안에서 동시 질의 둘이면 8 GB).
「1 GB」 를 말하던 다섯 곳(계획 C-2 · P1 · 리스크, 체크리스트, 이 노트 §9)을 같은 커밋에서 고쳤다. [[feedback-flip-premise-sweep]]

## 12. StepForge 가 P0 를 바로 해 왔다 — C-5 · C-6 꼴 초안이 섰다
덱(MinimumModel.k)을 받자마자 실제 잡 함수로 쟀다. 대응표 20/22, 가중치 1초 안. 빠진 둘(PID 20 · 21)은 덱 리더가 「누운 쐐기」 축퇴 꼴을 못 읽어서다 — 우리 덱의 결함이 아니라 그쪽 리더의 빈자리다.
C-6 꼴은 우리(브라우저 뷰어) 의견 넷을 그대로 받았다 — row_ptr uint32(JS 의 BigInt64 회피) · 배열 오프셋 8의 배수(TypedArray 를 복사 없이) · col 은 FE 절점 id(S1 순서에 묶이지 않게) · 행 ↔ glb 정점 고정(판 열쇠로 묶어 어긋나면 거절).
각도별 덱이 템플릿과 절점 · 요소 번호가 같다는 것을 우리가 확인해(100각도 전수) 가중치를 한 번만 셈하게 됐다. 새 결정 D-9(USD 를 누가 만드나)가 생겼다 — 권장은 SceneForge, 정하는 것은 사용자다.
SceneForge 몫의 질문(렌더용 삼각화 — 파트 대각선 비율 편차)은 담당이 없어 SceneForge 계획의 P0 질문에 올렸다.

## 13. 요청서 발송 — StepForge 는 닿았고 포털은 보류
StepForge 요청을 보내는 도중 안전 분류기가 응답을 끊었다. 메시지는 이미 닿아 StepForge 가 받아 P0 까지 했다. 포털 요청은 같은 꼴의 발송이라 혼자 다시 보내지 않고 사용자 확인을 기다린다.

## 14. 공유본은 Claude Docs, 원문은 리포
「낙하 트윈 계획」 문서(총괄 · SceneForge 두 탭, 교환 흐름 그림 · P0 진행표 · 결정표)를 만들었다. 사람이 읽고 댓글을 다는 곳이다. 다른 세션은 리포 파일을 읽으므로 원문은 리포에 둔다 — 바뀌면 리포를 먼저 고치고 옮긴다.

## 15. 무거운 P0 실측은 상한을 걸고
이 박스는 earlyoom 이 남의 프로세스를 죽인다. 실측마다 `prlimit --as`(8~12 GiB) · `taskset` · MemAvailable ≥ 30 GB 확인을 걸었다. 18 GB d3plot 을 다루는 S1 · 단면 영상 실측은 같은 조건으로 백그라운드에 맡겼다. [[box-earlyoom-collateral]]

## 16. SceneForge 리포는 아직 안 만들었다
계획대로 리포 생성은 P1(이름 확정 뒤)이다. 이름은 사용자가 맡겼지만 리포 · HEAX 등록은 되돌리기 비싸고 GitHub 생성은 밖으로 나가는 일이라, 지금 만들지 사용자에게 물었다. [[feedback-confirm-naming]]

## 17. Kit-CAE 는 HDF5 를 못 읽는다 — D-2 의 근거 하나가 틀렸다 (10-28 조사)
§8 의 「제안서 기준 Kit-CAE 가 HDF5 를 기본으로 받는다」 는 틀렸다. Kit-CAE 3.0 의 가져오기 목록은 CGNS · EnSight Gold · VTK · NumPy 등이고 HDF5 · Zarr · d3plot 은 없다(원문 재확인). 공식 충돌 예제도 결과를 EnSight Gold 로 바꿔 쓴다.
D-2(S1 = HDF5)의 권장은 그대로다 — 정본 추출본은 DynaForge 의 것이고 KooD3plotReader 가 이미 쓴다. 바뀐 것은 SceneForge 의 길이다. C-6 로 CAD 정점에 옮긴 변형을 USD 시간 샘플로 **직접** 쓰고(장면 계획의 변형층이 원래 그 꼴이다), Kit-CAE 는 FE 메시 위 필드를 볼 때만 EnSight Gold · VTK 로 바꿔 쓴다.
같이 나온 것 — Omniverse 는 2026-05 부터 개발 · 운영 · 재배포가 무료다(FAQ 원문 확인). 지원만 NVAIE 유료다. 약관 본문과 NGC 다운로드 페이지는 아직 유료로 적어 NVIDIA 서면 확인이 남았다. RTX PRO 6000 은 `+gfx` MIG 프로파일이 있으나 Kit RTX 실동 기록은 없어 노드 시험이 남았다.
「Kit-CAE 가 HDF5 를 받는다」 를 말하던 자리(총괄 D-2, SceneForge 계획 세 곳)와 라이선스 · MIG 리스크 넷을 같은 커밋에서 고쳤다. 전문 `docs/04-report/sceneforge-p0-research-1028.report.md`. [[feedback-flip-premise-sweep]]

## 18. S1 원형 — 각도당 0.2–0.7 GB, 게이트는 자명한 파트가 대부분 (10-28 실측)
11각도를 상태 4,952개 전부로 쟀다. 16비트 양자화 + int8 델타 원형이 각도당 204–670 MB(d3plot 18.2 GB 의 1.1–3.7%)다. 1,000각도면 0.2–0.7 TB 라, 각도 단위 복사(D-3)는 되지만 「통째로 cae00 에 둔다」 는 안 된다.
크기는 압축 방식보다 **양자화 스케일**이 정했다 — 전역 VM 스케일이 국소 피크에 묶이고, 델타 하나만 넘쳐도 단계를 통째로 저장해 델타가 거의 안 쓰였다. P1 의 정식 꼴은 파트별 스케일 · 값 단위 예외 · libver latest · 상태 솎기를 먼저 재고 정한다. 실제 `HDF5Writer` 는 원형과 꼴이 달라 그 숫자는 아직 없다.
게이트 22파트 중 21개는 모든 요소가 겉면이라 자명하다. 내부 요소가 있는 사면체 파트 1 만 판정이 의미 있고, 2/11 각도에서 내부 최대(겉면 −0.65% · −4.84%)였다 — 규칙대로다. 정본 대조는 deep report 두 각도에서 44/44 같았다.
표면 규칙에 함정이 하나 있었다 — 육면체 6면만 쓰면 사면체(N4 반복)가 가짜 사각면을 만들어 전부 겉면이 된다. 파일과 규칙을 StepForge 에 보냈고, 그쪽 20파트 면 집합이 S1 과 같았다. 못 짓던 PID 20 · 21(누운 쐐기)도 같은 규칙으로 같아져, StepForge 는 P1 덱 리더 보강을 이 일반 규칙으로 하기로 했다. 표면 규칙은 C-3 계약에 적었다. StepForge 는 자기 덱 겉면을 정본으로 두고 S1 과 집합이 같은지만 보는 꼴을 권했다 — 원칙 1(정본 하나)과 맞다.
읽기가 시간의 대부분이다(각도당 82–173 초). 정식 S1 을 이미 d3plot 을 통째로 읽는 후처리(deep report 34 GB RSS)에 얹을지 따로 돌릴지는 P1 에서 정한다.

## 19. 단면 영상 — 느린 까닭은 세션 수와 프레임 수다, GPU 는 절반의 절반 (10-28 실측)
§2 의 셋을 쟀다. ① 잡 폭증 — 운영 기본은 각도마다 LS-PrePost 세션 144개다(개관이 두 번 들어가는 중복 3 포함). ② 재열기 — 세션마다 18 GB 를 다 읽고, HDD 에서는 열기만 50–146 초다. ③ 소프트웨어 GL — NVMe 에서 프레임당 20 ms 중 래스터는 약 10 ms 다.
그리고 넷째가 있었다 — **프레임 수 = 상태 수**다. 4,952 프레임을 다 그려 24 fps 로 206 초짜리 영상이 나온다. 시간은 프레임 수에 정확히 비례한다. 34초 기록은 상태가 적은 덱이었을 것이다(추정 약 1,600).
그래서 GPU(viz 노드)는 movie 를 최대 2배 줄일 뿐이고, 큰 몫은 세션 수(144)와 프레임 수(4,952)를 줄이는 데 있다 — 프레임 솎기 · 개관 중복 제거 · 파트별 영상은 요청 때(S3) · 한 세션 여러 단면(NVMe 7–10%, HDD 에서는 더) · S1 기반 그리기(18 GB 읽기 없음). 무엇을 고칠지는 P1 에서 사용자와 정한다.
더 급한 것 — 운영 영상이 **오류 없이 틀린다**. 24개 중 7개가 어느 프레임부터 응력 0 으로 그려졌고(직접 확인), software 백엔드는 상태 1/3 만 읽고 rc 0 이었다. 둘 다 KooD3plotReader 몫이라 결함 보고를 사용자에게 물었다. [[kooremapper-green-gates-lie]]
