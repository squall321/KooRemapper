# 코어와 잇기 — DynaForge 몫 SRC-08 ~ 11 (2026-11-10)

## 무엇을 · 왜
cae00 운영의 11-09 제안서 「플랫폼 데이터 온톨로지화 · 코어와 잇기」 가운데 KooRemapper(DynaForge) 몫이다. 원문은 HWAXPortal 리포
`docs/core-link/request.md` 3-2절, 계약은 같은 리포 `docs/core-link/design.md` §8(포털 main `5f28bf36`)이다. 운영 실측(요청서 1-1) — 정의는
있으나 객체 0 · 코어로 가는 선 0 · 거울 받기가 기본 세 타입만 돌고 나머지는 10-28 에 멈춘 채 상태가 `ok` 로 보였다.

## 사용자 결정
- Q-5(11-09, 포털 결정 기록 CK-2) — 다리 **셋 다 · 정확 일치만**: `cae_part` → 코어 `part` · `cae_finding` → `failure_mode` · `cae_campaign` →
  `analysis_method`. 이름 · 별칭이 하나로 맞을 때만 `rule` 선, 나머지는 후보. 다시 반입해도 사람 선은 남는다. 다리는 자체 정의
  `dynaforge-core.json` 에 두고 바이트 사본인 정본 어휘 `dynaforge-cae.json` 은 고치지 않는다.
- 관계 이름(11-10) — `maps_to`(cae_part → part · StepForge SRC-02 와 같은 이름 — 한 질의로 두 앱을 묻는다) · `indicates`(cae_finding →
  failure_mode) · `follows_method`(cae_campaign → analysis_method).
  (11-14 덧붙임 — `maps_to` 는 이름만이 아니라 **정의가 같다**(아래 겹침 결정의 공통 블록). 「한 질의」 는 `cae_part` · `part_role` · `part`
  셋이 다 코어 공개인 허브에서만 선다 — 하나라도 닫혀 있으면 SP 코어 API 가 그 관계를 통째로 안 연다(아래 「허브에 올릴 때 알릴 것」).)
- 후보를 사람 선으로 확정 · 지우는 권한(11-10) — 리포트 주인 + 시스템 관리자(꾸러미 붙이기와 같다).
- 과제 비교 · 이력의 리포트 수치(11-11) — **읽을 수 있는 리포트만**(소유 · 같은 소속, 시스템 관리자는 전부). 과제 · 개정 자체는 회사
  전체 그대로. SRC-09 자동 잇기가 리포트를 과제에 저절로 이어 보이는 리포트가 늘어나서다(SRC-10 · 10-31 과 같은 까닭).
- `maps_to` 겹침(11-11) — **StepForge 와 정의를 하나로 맞춘다.** 두 앱이 바이트 같은 블록을 싣는다(출발 part_role · cae_part,
  basis human · other · rule, 선택 속성 여섯). 제안 블록을 StepForge 에 보냈다(아래 결정 기록).
- 그만 쓴(deprecated) 코어 객체(11-12) — **살아 있는 것이 먼저.** 다리(SRC-08)도 과제 잇기(SRC-09)도 살아 있는 객체가 정한다. 그만 쓴 것은 살아
  있는 맞음을 막지 못하고, 살아 있는 것이 하나도 안 맞을 때만 센다(하나면 잇는다 — 다리는 그 선에 `dst_deprecated` 를 단다 · 여럿이면 못 붙임).
- `revision_of` · `supersedes` 겹침(11-12) — **설명만 고치고 둔다.** 우리 정의(끝 타입 `dev_revision`)는 그대로다. StepForge 는 끝이
  `cad_revision` 이고 그쪽 `supersedes` 는 transitive 가 아니다 — 이름만 같고 정의가 다르다. 「같은 이름이라 한 질의로 묻는다」 는
  약속(`ontology-graft` 계획의 표 · 맥락 노트 결정 2)은 거뒀다. 두 앱의 정의를 한 허브에 함께 싣기 전에 이 둘을 맞춰야 한다(나중에 넣은 쪽이 앞
  정의를 덮는다).
- 기계 잇기 둘(11-12) — **허브에 있으면 판정을 따른다.** 허브에서 풀리는 이름(하나로 맞음 · 엇갈림)은 인제스트 · 메타 고침도 자동 잇기와 같은
  판정을 따른다. 엇갈리면 잇지 않고, 규칙으로 이미 바르게 이은 선은 그대로 둔다. 허브에 아예 없는 이름만 예전처럼 글자 그대로 잇는다 — 허브 없는
  박스(dev)와 허브에 아직 없는 과제는 동작이 그대로다. 고르지 않은 것 — 「한 판정으로만 잇는다」 · 「인제스트 때 잇기를 없앤다」. (11-14 조정
  세션의 읽기 — 끝이 거울에 없는 우리 별칭만 맞는 이름도 「허브에 아예 없는 이름」 으로 읽는다. 사용자가 뒤집을 수 있다 — 아래 결정 기록.)
- 보류(계약 §10 · 포털 11-09) — 가지(`corelink-src08-11`)에서 짓고 시험한다. main 에는 cae00 이 11-08 · 11-09 라운드 update-all 을 끝냈다고
  사용자가 알린 뒤(포털이 전한다)에 올린다 — deploy-all 이 코드와 Drive 바이너리를 함께 받기 때문이다.

## 지을 것
- **SRC-08 다리** — `dynaforge-core.json` 에 관계 셋. 꾸러미를 붙일 때(REST · 번들 · 7-1 반입 모두) 거울의 코어 객체 이름 · 별칭과 정확히 하나로
  맞으면 `rule` 선을 잇고, 여럿이 맞거나 부분만 맞으면 후보로 낸다. 결과에 선 수 · 후보 수 · 못 붙인 수를 싣는다(붙이기 응답 · 리포트의
  `ontology` 요약). 다시 붙이면 `rule` 선만 다시 짓고 **사람 선은 남긴다** — 리포트 행의 FK CASCADE 에 묶이지 않게 따로 두고, 가리키던 `cae_*` 가
  사라지면 지우지 않고 「끊긴 사람 선」 으로 보인다. 후보 확정 · 사람 선 지우기 길(REST, 리포트 주인 + 시스템 관리자). `report_cae` 가 선 · 후보를 보인다.
- **SRC-09 과제 잇기 자동** — `apply_task_links` 의 「붙는 것」(정확 · 별칭)만 받기(`plm_sync`) 뒤와 리포트 반입 뒤에 스스로 돈다. 받기 결과 줄에
  붙인 수 · 후보 수 · 못 붙인 수 · 이름 없는 리포트 수.
- **SRC-10 미리 보기 열기** — `GET /ontology/task-links`(MCP `plan_task_links`)를 일반 사용자 읽기로. 적용 `POST /ontology/task-links/apply` 는
  시스템 관리자 그대로(403). ★일반 사용자에게는 **자기가 읽을 수 있는 리포트(소유 · 같은 소속)만** 계획에 든다 — 일반 보기에서 `cae_*` 를 뺀
  10-31 결정과 같은 까닭(리포트 수치가 새어 나간다).
- **SRC-11 멈춘 타입** — 받을 타입(`sp_core_types`) 밖인데 거울에 남은 타입을 `ontology_sync_state` 의 타입 줄에 「멈춘 타입」 으로 표시하고
  `problems` 에 싣는다(기본값 셋은 그대로 — 넓히는 것은 박스 설정 BOX-01).
- 포털 쪽 — 게이트웨이 읽기 목록에 `heax-kooremapper_mcp:plan_task_links`(이름 · 쓰지 않는 미리 보기 성격 그대로).

- 같은 응답의 `mismatch` — 과제코드 · 별칭으로 적힌 리포트가 풀리는 과제의 그 판에 이어져 있으면 null(예전엔 `differs`). `renamed` · `merged` 는
  그대로이고 먼저 말한다. 엇갈린 이름으로 메타를 고쳐 선이 다른 판에 남으면 `differs`.
- PATCH /reports/{id}(MCP update_report_meta) — 응답 꼴은 그대로. project · dev_rev 가 든 저장은 풀리는 이름이면 그 과제의 판에 두고(`rule`),
  값이 같은 저장은 아무것도 안 쓴다(예전엔 규칙으로 이은 선을 글자 그대로의 판으로 되돌렸다). 엇갈린 이름이면 선을 옮기지도 떼지도 않는다.
  허브가 모르는 이름은 예전처럼 글자 그대로. 사람이 확정한 선 · 끊은 리포트는 그대로다.
- 끝이 거울에 없는 우리 별칭만 맞는 이름 — 글자 그대로 잇는다(`eng_meta`). 미리 보기 · 개정 보기는 여전히 `alias_missing` 을 보이고, 자동 잇기는
  별칭의 끝이 거울에 올 때까지 그 선을 옮기지 않는다.
- 허브 없는 박스(거울이 비어 있다) — 전부 예전과 같다. MCP — 도구 이름 · 인자 · 수는 그대로, 설명 다섯(ingest_report · update_report_meta ·
  report_revision · plan_task_links · confirm_task_alias)의 글만 바뀌었다.
- (조정 세션 덧붙임) 스위치 — 스위치가 꺼져 있는데 거울에 과제가 있는 박스(`KOORM_ONTOLOGY=0` 을 손으로 적고 허브 설정은 둔 박스 · 거울이 찬 뒤
  허브 설정을 뺀 박스)에서는 반입 · 메타 고침이 위 판정을 따르는데 반입 응답의 `task_links` 는 `skipped: off` 라, 하나로 안 정해지는 이름이 응답
  어디에도 안 잡힌다(소스로 읽음 · 돌려 재지 않았다). 그런 박스에서 글자 그대로 둘지는 사용자 결정 대기다(아래 결정 기록) — 정해지면 이 묶음을
