# 코어와 잇기 — DynaForge 몫 SRC-08 ~ 11 (2026-11-10)

## 무엇을 · 왜
cae00 운영의 11-09 제안서 「플랫폼 데이터 온톨로지화 · 코어와 잇기」 가운데 KooRemapper(DynaForge) 몫이다. 원문은 HWAXPortal 리포
`docs/core-link/request.md` 3-2절, 계약은 같은 리포 `docs/core-link/design.md` §8(포털 main `5f28bf36`)이다. 운영 실측(요청서 1-1) — 정의는
있으나 객체 0 · 코어로 가는 선 0 · 거울 받기가 기본 세 타입만 돌고 나머지는 10-28 에 멈춘 채 상태가 `ok` 로 보였다.

## 사용자 결정
- Q-5(11-09, 포털 결정 기록 CK-2) — 다리 **셋 다 · 정확 일치만**: `cae_part` → 코어 `part` · `cae_finding` → `failure_mode` · `cae_campaign` →
  `analysis_method`. 이름 · 별칭이 하나로 맞을 때만 `rule` 선, 나머지는 후보. 다시 반입해도 사람 선은 남는다. 다리는 자체 정의
  `dynaforge-core.json` 에 두고 바이트 사본인 정본 어휘 `dynaforge-cae.json` 은 고치지 않는다.
- 관계 이름(11-10) — `maps_to`(cae_part → part · StepForge SRC-02 와 같은 이름 — 한 질의로 두 앱을 묻는다) · `indicates`(cae_finding →
  failure_mode) · `follows_method`(cae_campaign → analysis_method).
- 후보를 사람 선으로 확정 · 지우는 권한(11-10) — 리포트 주인 + 시스템 관리자(꾸러미 붙이기와 같다).
- 보류(계약 §10 · 포털 11-09) — 가지(`corelink-src08-11`)에서 짓고 시험한다. main 에는 cae00 이 11-08 · 11-09 라운드 update-all 을 끝냈다고
  사용자가 알린 뒤(포털이 전한다)에 올린다 — deploy-all 이 코드와 Drive 바이너리를 함께 받기 때문이다.

## 지을 것
- **SRC-08 다리** — `dynaforge-core.json` 에 관계 셋. 꾸러미를 붙일 때(REST · 번들 · 7-1 반입 모두) 거울의 코어 객체 이름 · 별칭과 정확히 하나로
  맞으면 `rule` 선을 잇고, 여럿이 맞거나 부분만 맞으면 후보로 낸다. 결과에 선 수 · 후보 수 · 못 붙인 수를 싣는다(붙이기 응답 · 리포트의
  `ontology` 요약). 다시 붙이면 `rule` 선만 다시 짓고 **사람 선은 남긴다** — 리포트 행의 FK CASCADE 에 묶이지 않게 따로 두고, 가리키던 `cae_*` 가
  사라지면 지우지 않고 「끊긴 사람 선」 으로 보인다. 후보 확정 · 사람 선 지우기 길(REST, 리포트 주인 + 시스템 관리자). `report_cae` 가 선 · 후보를 보인다.
- **SRC-09 과제 잇기 자동** — `apply_task_links` 의 「붙는 것」(정확 · 별칭)만 받기(`plm_sync`) 뒤와 리포트 반입 뒤에 스스로 돈다. 받기 결과 줄에
  붙인 수 · 후보 수 · 못 붙인 수 · 이름 없는 리포트 수.
- **SRC-10 미리 보기 열기** — `GET /ontology/task-links`(MCP `plan_task_links`)를 일반 사용자 읽기로. 적용 `POST /ontology/task-links/apply` 는
  시스템 관리자 그대로(403). ★일반 사용자에게는 **자기가 읽을 수 있는 리포트(소유 · 같은 소속)만** 계획에 든다 — 일반 보기에서 `cae_*` 를 뺀
  10-31 결정과 같은 까닭(리포트 수치가 새어 나간다).
- **SRC-11 멈춘 타입** — 받을 타입(`sp_core_types`) 밖인데 거울에 남은 타입을 `ontology_sync_state` 의 타입 줄에 「멈춘 타입」 으로 표시하고
  `problems` 에 싣는다(기본값 셋은 그대로 — 넓히는 것은 박스 설정 BOX-01).
- 포털 쪽 — 게이트웨이 읽기 목록에 `heax-kooremapper_mcp:plan_task_links`(이름 · 쓰지 않는 미리 보기 성격 그대로).

## 포털 · 계약에 알릴 것 (SRC-08)
- 관계 셋 — `maps_to`(cae_part → part · 다대일 · StepForge part_role → part 와 같은 이름 — 한 질의로 두 앱) · `indicates`(cae_finding →
  failure_mode · 다대다) · `follows_method`(cae_campaign → analysis_method · 다대일). 정의는 `platform/core/ontology/dynaforge-core.json`.
- 쓰는 길은 REST 둘 — `POST /reports/{id}/cae/bridges`(본문 `src_key` · `dst_key` · `dst_type?` · `relation?` · `note?`) ·
  `DELETE /reports/{id}/cae/bridges?src_key=&dst_key=`. 리포트 주인 · 시스템 관리자만(같은 소속 읽기 403 · 못 읽는 사람 404).
  **MCP 도구는 늘지 않았다** — 보기는 `report_cae` 의 `bridges`(읽기)라 게이트웨이 읽기 · 쓰기 목록에 더할 것이 없다.
- 붙이기 응답 · 리포트 `ontology` 요약의 칸 — `bridges.rule` · `human` · `stale`(선 수) · `candidates` · `unmatched` · `unnamed`(선이 없는
  객체 수) · `by_type` · `mirror`(거울의 타입별 살아 있는 건수) · `notes`. 7-1 반입은 잡 원장 `external_ref.ontology.bridges`, 번들 반입은
  응답 `ontology.bridges`.
- 다리 끝 타입은 **받을 타입에 있어야** 선다 — cae00 은 BOX-01(`KOORM_SP_CORE_TYPES=` 빈 값 — 전부)로 된다. 기본값(셋)인 박스는
  `notes` 가 까닭을 말한다.
- BOX-13 의 미리 보기(`--dry-run`)는 SRC-08 에 따로 없다 — 다리는 붙일 때 저절로 규칙 선만 긋고, 보기(`report_cae`)가 지금 거울로 센
  셈 · 후보 · `drift` 를 쓰지 않고 준다. 운영 박스는 리포트가 0 건이라 지금은 낼 것이 없다.
- 원문의 「꾸러미 붙이기와 같은 권리」 — REST 붙이기는 지금 **주인만**이다(관리자도 404). 사람 선 권한은 결정대로 주인 + 관리자로 지었다.

## 결정 기록
- (11-10) 위 사용자 결정. 원문의 Q-5 는 포털 결정 기록 CK-2 로 확인했다(전해 들은 말만으로 짓지 않는다).
- (11-10) 미리 보기를 일반 사용자에게 열 때 보이는 리포트만 — 계획은 지금 모든 리포트를 읽는다(`select(ImpactReport)`).
- (11-10) **SRC-08 카디널리티** — `maps_to` 다대일(덱 파트 하나는 부품 하나를 본뜬 것 · StepForge 와 같다) · `indicates` 다대다(소견 하나가
  고장모드 여럿을 가리킬 수 있다 — 규칙은 하나로 맞을 때 한 줄만 긋고 사람은 여럿을 잇는다) · `follows_method` 다대일(후처리 한 번은 한 방법).
  까닭은 정의의 `description` 에 적었다.
- (11-10) **부르는 칸** — 파트 `name`(덱 *PART 제목) · 소견 `title` · 캠페인 `scenario_kind`. 소견은 어휘(0.3 ~ 0.5)에 고장 종류를 따로
  적는 칸이 없고 제목이 판정 문장이다 — 대개 파트 이름 · 수치가 들어(「Part 3 (PCB): stress exceeds yield」) 규칙 선은 드물다. 제목 글이
  우리 별칭 표에 있으면 그 제목은 규칙 선이 된다(적는 길은 아래 남은 것). 소견마다 고장 종류를 싣는 칸은 다음 어휘 판(생산 쪽 몫)에
  묻는다 — 정본 어휘는 이번에 안 고친다(결정). 캠페인 종류는 닫힌 셋이라 별칭 셋이 있으면 모든 캠페인이 선다.
- (11-10) **정확 · 후보 규칙** — 정확은 과제 잇기(`resolve_task`)와 같다 — 앞뒤 공백만 걷고 글자 그대로(앱 안에 「정확」 하나). 코어 쪽 글은
  거울(허브 행 · 사라지지 않은 것)의 key · label · 허브 별칭(`properties.aliases`) · 옛 key(`onto_previous_keys`)와 우리 별칭 표(그 코어 타입 —
  사람 기록이라 먼저). 하나로 모일 때만 규칙 선, 여럿이면 후보. label 을 넣은 까닭 — 과제는 key 가 이름이지만 코어 part · failure_mode ·
  analysis_method 의 key 꼴은 아무도 모른다(dev 거울에 0 건 — StepForge 도 같은 까닭으로 대응표를 비웠다). 그만 씀은 정확히 맞으면 잇는다
  (resolve_task 와 같다). 후보는 task_candidates 와 같은 `normalize` — 여럿 · 구분기호 · 대소문자만 다름 · 한쪽이 품음(짧은 쪽 2자 이상) ·
  객체마다 다섯 · 그만 씀 제외.
- (11-10) **사람 선 저장** — 위임문의 예(`report_id` 를 비운다) 대신 `report_id` 를 그대로 두고 `basis: human` 으로 표시해, 다시 붙일 때 걷는 선
  (`attach_ontology` 의 명시적 delete)에서 뺀다. 까닭 — `report_id` 를 비우면 ① 전사 보기(`/ontology/objects/{t}/{k}` 의 in · out 은
  `report_id` 가 빈 선만 낸다)에 리포트 선이 새고(10-31 결정 위반 — 규칙 선은 안 보이는데 사람 선만 보이는 것도 이상하다) ② 리포트를 지워도
  남는다(0019 의 교훈 — 트리거를 하나 더 지어야 한다). FK CASCADE 는 리포트 행을 지울 때만 돌고 다시 붙이기에는 돌지 않는다. 열쇠는 해석 객체의
  안정 key(`<리포트 id>/part/<PID>`) — 다시 반입에 그 객체가 없으면 지우지 않고 「끊긴 사람 선」(stale)으로 보인다(확정 때 남긴 `src_label` 로).
- (11-10) **사람이 이긴다** — 다대일(파트 · 캠페인)은 사람 선이 있으면 규칙이 그 객체를 건너뛴다(확정이 다른 짝의 규칙 선을 밀어낸다 —
  응답 `replaced_rule`). 다대다(소견)는 함께 선다 — 다만 여럿이 맞아 갈리지 않은 것은 사람이 하나를 골라도 규칙이 나머지를 긋지 않는다.
  같은 짝의 규칙 선을 확정하면 그 줄이 사람 선으로 오른다. 규칙 선은 지우지 않는다(409 — 다시 지으면 다시 선다).
- (11-10) **다시 짓는 때** — 붙일 때마다(같은 바이트여도 — 행은 그대로 두고 다리만), 사람 선을 확정 · 지울 때. 거울 · 별칭이 바뀐 뒤 따로
  다시 짓는 길은 두지 않았다 — 같은 꾸러미를 다시 붙이면 된다. 보기는 저장된 규칙 선과 지금 셈이 다르면 `drift`(긋기 · 걷기 목록)를 준다.
  다리가 깨져도 꾸러미는 실리고 보기도 선다(그 칸만 `bridges.error` — 다리 쓰기는 리포트 행 잠금으로 한 번에 하나).
- (11-10) **권한** — 결정대로 리포트 주인 + 시스템 관리자. 같은 소속 읽기 사용자는 403(무엇이 막혔는지 말한다), 못 읽는 사람은 404(다른 리포트
  길처럼 리포트가 있다는 것도 알리지 않는다). ⚠ 관리자는 남의 리포트 다리 **후보를 못 본다** — `/reports/{id}/cae` 는 관리자에게도 주인 ·
  같은 소속만이다(그대로 뒀다 — 가시성은 사용자 판단). 관리자는 `find_cae_parts`(전사)로 해석 key, `ontology_find` 로 코어 key 를 보고 짝을
  확정할 수는 있다.
- (11-10) **검증기** — 다리 끝(part · failure_mode · analysis_method)을 바깥 타입(허브 거울)에 넣고, 관계에 붙는 칸도 타입 칸과 같은 눈으로 본다.
  우리 정의만 볼 때는 해석 어휘 타입을 함께 아는 눈으로 검사한다(합친 검사는 원래대로). 관계 · 칸 키가 SP 가져오기 칸 목록 안인지 대조했다
  (최상위 `_note` 는 원래부터 있던 키로 SP 가져오기는 이것을 거절한다 — 허브로 내보낼 일이 생기면 걷는다).
- (11-10) **SRC-08 시험** — 백엔드 전체 818 통과 · 16 실패 · 22 건너뜀. 16 은 바꾸기 전 바탕(795 통과)과 같은 16 이다 — 워크트리에 compat
  바이너리(`platform/backend/bin` — 넣지 않는다)와 supervisor 환경이 없어서다. MCP 계약 시험(MCP venv) 18 통과. 워크트리 API(`--lifespan off` —
  워커 없이) + 워크트리 MCP 임시 스택에 대고 `reports_smoke` 58/58(다리 값 항 셋 — impA 실물 꾸러미, dev 거울은 세 타입 0 이라 까닭 notes). 지키는
  자리 셋(사람 선 남기기 · 여럿이면 후보 · 사람이 이긴다)을 일부러 깨서 시험이 잡는 것을 봤다. 시험 · 스모크 뒤 dev DB 에 남은 것 0(거울 픽스처 ·

  과제만 적는다. 맞추기는 그 타입의 별칭을 보지만 지금은 DB 로만 들어간다. 서비스(`confirm_alias` · `remove_alias`)는 type_slug 를 받으니
