## 2026-10-14 · 결론이 두 번 바뀌었다

### 처음 생각 — "온톨로지를 옮긴다"

요청이 "온톨로지 부분을 심어 달라" 였으니 옮기는 것으로 읽었다. 재보고 접었다 —
백엔드 34,180줄 + 프런트 22,158줄이고 의존 폐쇄가 플랫폼 전체다. 결정적인 것은 규모가 아니라
**전제**였다. `objects` 는 **부서 소유**를 전제로 짜여 있는데(`visible_owner_clause`·
`require_owner_edit`·`resolve_owner_workspace`) DynaForge 에는 부서가 없다. 부서를 같이 들이면
인증·권한을 다시 설계하는 일이 되고, 그것은 심는 것이 아니라 **합병**이다.

### 두 번째 — "받기는 묶음 가져오기다" → **틀렸다**

`managed.py` 머리말의 "받기는 묶음 가져오기에 `source` 를 적어서만 한다" 를 읽고 그것이
쌍둥이가 받는 길이라고 적었다. 아니다 — 그 문장은 **허브 쪽**이 하는 일이다. 쌍둥이가 받는 길은
**코어 API** 이고, 받는 쪽 **키트와 규칙 열하나가 이미 있다**
(`coreapi/kit/sp_core_pull.py` 436줄 · `docs/외부-시스템-연동-지침서.md` §4.2).

**왜 놓쳤나** — `ontology`·`objects`·`datasources` 를 읽고 `coreapi` 를 안 봤다. 모듈 목록을
규모 순으로 재고 큰 것부터 읽었는데, `coreapi` 는 1,753줄로 중간이라 눈에 안 들어왔다.
**규모 순으로 읽으면 작고 결정적인 모듈을 놓친다.**

고친 계기는 **StepForge 의 같은 계획**이었다(`bea7485`, D-525). 거기 적힌 것을 그대로 믿지 않고
전부 실물로 대조했고(키트 436줄 · 규칙 11개 · `plm-core.json` 의 타입 넷 — **다섯이었다**,
`plm_test_site` 가 더 있다), 그 과정에서 제 오기를 찾았다.

## 결정 1 — StepForge 와 **용어·표 꼴·단계 번호**를 맞춘다

두 쌍둥이가 같은 허브에서 같은 것을 받는다. 설계가 갈리면 갈린 쪽은 한쪽만 고쳐진다
([[feedback-second-consumer-moment]] — 두 번째 소비자가 생기는 순간이 정본을 모으는 순간이다).

맞춘 것 — 용어(개정·허브·거울·수신자) · 문서 짜임새(§0~§7) · 단계 번호(S0~S6) ·
표 이름과 칸(`onto_types`·`onto_relation_types`·`onto_objects`·`onto_relations`·
`onto_sync_state` · `source`∈{hub, 자기}) · 끝점을 **`key` 로** 잇는 것 ·
"엔진이 아니라 꼴을 가져온다" · "개정 이름은 사람이 정하고 기계는 후보를 낸다".

안 맞춘 것 — HTTP 클라이언트(`requests` / **httpx**, 우리 관례) · **개정 타입의 slug**.

★**저장소를 여기 넣은 것이 틀렸다**(아래 결정 5). 처음엔 「맞추면 안 되는 것」 에 저장소를
넣었다 — StepForge 의 SQLite 를 **주어진 것**으로 놓은 탓이다. 그것 자체가 선택이었다.

## 결정 2 — 개정 타입을 **`dev_revision`** 으로, StepForge 와 **가른다**

둘은 **같은 꼴, 다른 축**이다.

| | StepForge `cad_revision` | DynaForge `dev_revision` |
|---|---|---|
| 뜻 | CAD 데이터 한 벌이 어느 과제·모델의 **몇 번째 판**인가 | 해석 결과가 어느 과제의 **어느 개발 단계·차수**인가 |
| 이름 | `C2` (`^[A-Z][0-9]$`) | `dv1`·`pv2`·`pre`·`mp` (`_STAGE_RE`) |

둘 다 같은 `plm_task` 에 매달린다. 허브에서 만날 수 있으므로 **slug 를 가른다.** 뜻이 같은
관계 이름(`revision_of`·`supersedes`)은 **똑같이** 쓴다 — 그래야 나중에 한 질의로 묻는다.

## 결정 3 — `eng_meta` 를 **지우지 않는다**

걷어내고 관계로 갈아타는 쪽이 깔끔해 보였지만, `eng_meta` 는 DataHub 등재 양식과 **같은 모양**
이고 필터·패싯이 이미 물려 있다(`services.py:826-910`). 걷어내면 DataHub 쪽까지 같이 손대야
한다. 그래서 **둘을 함께 두고, 어긋나면 관계를 정본으로 하되 어긋난 사실을 띄운다.**
조용히 맞추면 사람이 넣은 값과 저장된 값이 달라지고 그 차이는 아무 데도 안 뜬다(SP 가 속성
검증에서 같은 이유로 "반올림하지 않고 거절한다" 고 적었다).

## 결정 4 — 엔진을 **작게 다시 짓는다**(메타모델을 데이터로 두지 않는다)

SP 처럼 `object_types` 를 데이터로 두면 화면 자동생성·권한·`list_view`·인터페이스가 줄줄이
따라온다 — 그것이 34,180줄의 정체다. 지금 필요한 축은 **허브 거울 넷 + 자체 하나**다.

**다시 볼 기준을 지금 적는다** — 축이 늘어 **화면 자동생성이 필요해지는 날**, SP 인스턴스를
따로 띄우는 쪽(계획서의 옛 선택지 B)을 다시 본다. 기준을 안 적으면 "작게" 가 영원히 작게 남고,
작게 남은 것은 결국 큰 것을 어설프게 흉내 낸다.

## 관찰 — SP 의 수신 규칙 둘은 우리가 이미 겪은 함정이다

- 규칙 2(「`next` 가 있으면 `as_of` 는 `null`」) — 중간에서 멈춘 쪽이 남은 쪽을 **영영 안 받는다**.
  DynaForge 의 외부 잡 폴링에서 같은 성질의 것을 막았다(모르면 접지 않는다).
- 규칙 7(「`since` 없이 받으면 지워진 것은 안 온다」) — **빈 응답을 「없다」 로 읽는** 함정이다.
  리포트 블록 작업에서 "빈 목록은 데이터가 없다 로 읽힌다" 로 같은 결론에 닿았다.

받는 코드를 쓸 때 이 둘을 **회귀로** 먼저 박는다.


## 결정 5 — 저장소는 **Postgres 로 맞춘다** (2026-10-14 · 사용자 지시)

처음 판에서 저장소를 「맞추면 안 되는 것」 에 넣었다. 사용자가 "postgres로 바꿔야하지 않을까?
전체 플랫폼들과 규격을 맞춰야지" 라고 했고, 그것이 맞다. 재보니 —

- SP 는 **PG 필수**, 그 포크 넷도 PG, DynaForge 도 PG(5436). **StepForge 만 SQLite** 다.
- 그리고 **StepForge 자기 계획서가 이미 그렇게 적어 뒀다** — `StepForge/docs/PLAN.md:51`
  `| DB | SQLite(WAL) → **필요 시 PG** | 초기 규모에 충분 |`. 새 결정이 아니라 **예정된
  전환의 「필요 시」가 온 것**이다.
- 지금 구조는 PG 가 기본으로 주는 것을 흉내 내고 있다 — `db.py:604` 가 `BEGIN IMMEDIATE` 를
  "`SKIP LOCKED` **대용**" 이라고 스스로 적고, `PRAGMA journal_mode=WAL` 잠금 충돌을 따로
  다뤄야 했다(D-506). DynaForge 는 같은 자리에서 **진짜** `FOR UPDATE SKIP LOCKED` 를 쓴다.
- 비용은 실측으로 **모여** 있다 — `sqlite3` 12파일(집중 3) · 스키마 620줄/18표 · 전용 문법
  ~44지점 · `?` 256회. 운영 선례가 DynaForge 에 그대로 있다(`infra/scripts/start.sh`·`backup-db.sh`).

**이 결정이 바꾸는 것** — 표가 이름만 같은 게 아니라 **DDL 이 같아진다**(`properties` 가 양쪽
다 JSONB). 그래야 두 쌍둥이 사이에 데이터가 **실제로** 옮겨진다. "규격을 맞춘다" 의 뜻이
거기다.

**이 결정이 안 바꾸는 것** — DynaForge 의 「엔진을 작게 다시 짓는다」. 막는 것이 DB 가 아니라
**부서**였다. 그리고 ★**부서 표는 들이면 안 된다** — DynaForge 는 게이트웨이가 HMAC 로 서명한
`X-Heax-User-Affiliation`+`X-Heax-Aff-Proof` 를 받고 `shared/affiliation.py`·
`shared/visibility.py` 가 판정한다(정본은 포탈). SP 스스로 §3.6 에 적었다 —
"부서를 `objects` 에 복제하면 두 벌이 되고 **반드시 갈린다**". 그래서 `kind_class=system`
거울(행 복제 0)이다. **규격을 맞추는 것은 표를 베끼는 것이 아니라 규칙을 따르는 것이다.**

**StepForge 쪽에 생기는 질문** — 「엔진이 아니라 꼴만」 의 근거가 "StepForge 는 SQLite 다" 였다
(그 문서 §2). PG 가 되면 SP 의 엔진(JSONB·pg_trgm·재귀 CTE·advisory lock·`SKIP LOCKED`·`COPY`)이
**쓸 수 있는 것**이 된다. 그것은 StepForge 의 판단이고, 여기서는 사실만 적는다(§7 ⑨).


## 결정 6 — 보관은 **submodule**, 토큰은 **`.env`** (2026-10-14 · 사용자 "`.env` 서브모듈")

StepForge 가 먼저 S0 을 닫았다(`d8f5bed`) — `external/StandardPlatform` submodule,
`f7485c0` 고정, 브랜치 추적 없음, 런타임 import 금지 구조 시험. **같은 경로·같은 주소·같은
커밋**으로 맞췄다. 같은 참고본을 봐야 두 쌍둥이의 결이 맞는다 — 판이 갈리면 「그 문서 §4.2」
같은 인용이 서로 다른 것을 가리킨다.

경로를 `vendor/` 에서 `external/` 로 옮겼다. DynaForge 에 `third_party/tetgen` 이 있지만
그것은 **베껴 넣은 소스**이고, submodule 참조는 성질이 다르다 — StepForge 의 `external/` 을 따른다.

토큰은 **`.env`** 다. 제가 드린 양자택일("`.env` 관례 유지 \| 파일 경로로만")에 대한 답이다.
`platform/**/.env` 가 `.gitignore` 에 있으므로 「비밀은 리포에 두지 않는다」 와 어긋나지 않는다.
StepForge 는 `/data/hwax/secrets` 아래 **경로만** 앱에 준다(D-525 ②) — 그쪽이 규격을 `.env` 로
맞출지는 거기서 정할 일이고, 여기서는 적어만 둔다.

### ★관문이 안 무는데 초록이었다 — 범위를 0으로 훑고 있었다

경계 시험을 쓰고 `tools/_boundary_probe.py` 에 `sys.path.insert(0, "external/…")` 를 **일부러**
심었는데 **4항 전부 초록**이었다. 원인은 `git ls-files` 가 **추적된 것만** 보는 것이었다 —
방금 쓴 파일은 미추적이라 목록에 아예 없었다. 초록이었던 이유가 "깨끗해서" 가 아니라
**"안 봐서"** 다.

`--cached --others --exclude-standard` 로 고쳤다(추적된 것 + add 안 한 것, `.gitignore` 가
`.venv`·`venv` 를 막아 준다). 고친 뒤 다시 심으니 빨갛고, 지우니 초록이다.

그리고 그 실수가 다시 안 나오게 **관문 자신에게 관문을 달았다** —
`test_the_scan_actually_covers_the_runtime` 이 훑은 파일 수가 50을 넘는지 본다.
[[kooremapper-green-gates-lie]] 의 "수를 세는 관문은 자리를 못 본다" 와 같은 성질이다.
**세는 관문이 0을 세면 언제나 초록이다.**
