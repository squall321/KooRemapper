# 미뤄 둔 결함 둘 — 맥락 · 결정 기록 (2026-11-20)

계획 `deferred-defects-1120.plan.md` · 체크리스트 `deferred-defects-1120.checklist.md`.

## 1. 왜 지금 · 왜 이 둘
- 11-08 사용자 결정으로 「다음 판」 에 미뤘던 것이다(운영 판에도 있는 기존 결함). 11-20 남은 일 정리에서 「물성을 조용히 바꾸는 것 먼저」 로
  이 둘을 권했고 「진행해줘」 를 받았다.
- 다섯 가운데 둘만 한다 — 권한 범위가 둘이었다. 나머지 셋은 계획 0절에 이름만 남긴다.

## 2. F-1 — 잰 차례
- 탐침(scratch — 리포에 없다)이 dev 라이브러리를 물고 `ConnectivityAnalyzer` → `StructuredGridIndexer::assignIndices` 를 돌려 요소마다 (i,j,k)
  를 모았다. 서로 다른 칸 수가 unfold 가 쓴 요소 수와 **정확히 같았다**(53 · 238) — 손실은 색인 충돌 하나로 설명된다.
- 위상 색인 시제품(같은 탐침)은 시작 모서리의 세 이웃 면에 축을 붙이고, 이웃으로 넘어갈 때 「맞닿은 면 = 같은 축 반대 부호 · 그 맞은편 = 같은 축
  같은 부호 · 나머지 네 면은 맞닿은 면과 두 절점을 나눠 가진 이쪽 면의 축」 으로 틀을 옮긴다. 같은 요소에 두 길이 다른 칸을 주면 충돌로 센다.
  색인이 된 덱 전부에서 충돌 0 · 칸 전부 유일.
- 「지금 = 위상」 은 요소마다 칸이 같다는 뜻이다(축 이름 · 방향을 맞춘 뒤 — 지금 색인기는 끝에 축을 크기순으로 다시 놓는다).

## 3. 결정
- **A 를 짓고 B 는 내놓기만 한다.** A 는 「조용한 손실」 을 「큰 소리의 거절」 로 바꾸는 가장 작은 고침이고 DF-14 에서 사용자가 고른 갈래와
  같다. B 는 `map` 의 뿌리(모든 매핑 산출이 이 색인을 탄다)를 바꾸므로 혼자 정하지 않는다 — 수치(83 같음 · 8 새로 됨)와 함께 묻는다.
- 유일성 검사는 채움률 검사 **뒤**에 둔다 — 지금 채움률로 실패하는 다섯 덱의 오류 글을 바꾸지 않는다(그 글을 읽는 시험 · 사람이 있을 수 있다).
- 이미 색인이 든 메시(`allAssigned` 갈래)는 건드리지 않는다 — 덱에서 온 메시는 그 갈래를 타지 않는다.
- unfold 의 요소 수 검사는 「읽은 수 = 지은 수」 하나다. 까닭은 색인기 글(A-1)이 말하고, A-2 는 색인이 멀쩡한데 3단계가 건너뛴 경우의 뒷문이다.

## 4. F-2 — 결정
- 여섯 자리를 폭에 맞춘다(거절 글만 고치는 길보다 — 절점 · 요소 · 세트는 이미 long 을 읽고 쓰기는 줄을 그대로 옮겨, 남은 것이 첫 칸 읽기뿐이다).
- `indexDeck` 에서는 이미 키워드마다 재는 폭(`setW`)을 그대로 쓴다 — 이름을 `cardW` 로 바꿔 `*PART` · `*SECTION_SOLID` · `*SET_PART` 가 같이
  쓴다.

## 5. 계획을 쓴 뒤 더 잰 것(F-1)
- unfold 를 리포 덱 339 개에 돌렸다(고치기 전 바이너리). 읽은 수 = 쓴 수 83 · **잃음 3**(`test_small_bent.k` 100 → 53 · `wave_bent.k`
  250 → 238 · `examples/teardrop/teardrop_mapped.k` 2,000 → 1,214) · 거절 253. 색인 탐침의 「칸이 겹친 덱」 과 같은 셋이다 — 겹침 말고 다른
  까닭의 손실은 나오지 않았다.
- 구멍 난 격자(상자 10×5×2 에서 요소를 뺀 것)는 잃지 않는다. 안쪽 요소 하나 · 둘을 빼면 rc 0 으로 99 · 98 을 다 쓰고, 모서리 요소나 한 줄을
  통째로 빼면 검증기가 rc 1 로 막는다(「Element N has 2 neighbors (expected 3-6)」). 그래서 평판 생성 3단계의 「칸이 비면 건너뛴다」 는 겹침
  말고는 잃는 사례를 찾지 못했다 — A-2 는 실패 사례가 있어서가 아니라 연산이 제 불변식을 스스로 지키게 하는 뒷문이다.
- `map` 의 굽은 기준으로 넣으면 세 덱 모두 rc 1 이었다(뒤의 모서리 절점 검사 — 「only 0/8 · 1/8 corner nodes found」). **조용히 틀린 `map`
  산출은 찾지 못했다(재지 못한 것 — 그런 덱이 리포에 없다).**

## 6. 고친 뒤 잰 것(F-1)
- 새 시험은 고치기 전 빨강 넷(U-1 · U-2 · M-1 · M-2) → 고친 뒤 14 항 초록.
- 변이 확인 — A-1 을 잠시 끄고 지으면 세 덱 모두 A-2 가 rc 1 로 막는다(「Unfold lost elements: generated 53 of 100」 · 238 of 250 ·
  1214 of 2000 — 산출 없음). 되돌려 다시 지었다.
- 같은 339 덱을 다시 돌리면 같음 83 · 잃음 0 · 거절 256(253 + 3) — 멀쩡하던 83 덱은 그대로다.
- `map` 의 거절 글이 뒤의 모서리 검사에서 색인 겹침(「12 of 250 elements share an (i,j,k) slot …」)으로 앞당겨졌다. rc 는 전과 같다(1).
- **예제 파일만의 일이 아니었다.** 전제 문장을 쓸다가 `generate` 의 굽힘 종류 11 × 크기 3(20×5×3 · 40×8×4 · 10×10×2)을 지어 unfold 했다.
  33 가운데 28 은 요소 전부 · **둘은 겹침**(helix 20×5×3 300 → 127 · wave 10×10×2 200 → 127 — 고치기 전 rc 0, 이제 rc 1) · 셋은 전부터
  채움률로 거절(scurve 40×8×4 · scurve 10×10×2 · helix 10×10×2). 이 다섯을 위상 색인 시제품에 넣으면 다섯 다 칸이 유일하다(충돌 0).
  겹친 둘을 `map` 의 굽은 기준으로 넣으면 고치기 전에도 rc 1 이었다(모서리 절점 1/8 · 4/8) — 생성기가 지은 짝을 `map` 이 못 쓰는 것은
  전부터의 한계고, 선택지 B 가 푸는 자리다. 시험에 U-6 으로 넣었다.
- 매뉴얼 9장 주의사항에 거절을 적었다. 도움말 · MCP 설명에는 unfold 가 요소를 지킨다 · 잃는다고 말하는 문장이 없어 그대로 둔다.
- 단위 시험 231/231 · 회귀 132 파일 전부 rc 0(gmsh 환경 변수 둘을 준 채).

## 7. 고친 뒤 잰 것(F-2)
- 고친 자리는 일곱이다(계획은 여섯). 일곱째는 되읽기의 재질 셈 — `matids::inUse` 에 `*MAT` 블록 줄만 넘겨, 공용 훑기(`matids::scan`)가 덱 폭을
  `*KEYWORD` 줄에서 읽지 못하고 long 재질의 MID 를 0 으로 셌다(「미정의 재질」 rc 1). `*KEYWORD` 줄을 같이 넘긴다 — 훑기는 구조 재질
  키워드가 아닌 줄을 건너뛴다.
- 폭 규칙은 Vol_I 로 확인했다 — long 은 표준에서 20칸 이하인 칸이 다 20칸(19315-19316) · 표준 덱의 접미사 `+` 는 그 키워드만 long, long 덱의
  접미사 `-` 는 그 키워드만 표준(19342-19348).
- 새 시험 21 항 — 고치기 전 빨강 12(L-1 ~ 4 · P-1 ~ 4 · N1 · N2 · V-1 · R-2) → 고친 뒤 전부 초록. M(long 덱 + 접미사 `-`) 넷은 고치기 전에도
  초록이다 — 과하게 고쳐 표준 폭 카드를 20칸으로 읽지 않는지 보는 지킴이로 둔다. N1 · N2(없는 재질 · 없는 섹션)는 long 에서도 되읽기가
  세는지 본다(되읽기가 0 만 내는 것이 아닌지).
- 변이 여덟 — 자리마다 예전 꼴로 되돌려 짓고 새 시험을 돌렸다. 다 빨갛다(빨간 항 수 — `indexDeck` `*PART` 12 · `*SECTION_SOLID` ELFORM 5 ·
  패스 2 `*PART` 12 · `*PART_*` 변형 1 · ID 블록 12 · 재질 훑기의 덱 폭 7 · 되읽기 `*SECTION` 11 · `indexDeck` 접미사 무시 4). 되돌린 소스는
  보관본과 sha 가 같다.
- 접미사를 무시하는 변이에서 M 은 빨개지지 않는다 — `cardFields` 는 칸 안에 빈칸이 끼면 공백 토큰으로 갈음해, 10칸 카드를 20칸으로 읽어도
  값이 같다. 접미사 지킴이는 P(표준 덱 + `+`)다. 같은 갈음이 아래 폭이 섞인 산출을 되읽기가 못 잡는 까닭이다.
- 리포(작업 트리 · 주 체크아웃)에 long 덱이 없다 — **실물 long 덱으로는 재지 못했다.** 솔버로도 못 쟀다(라이선스 만료).
- 도움말 · MCP 설명에 extract-parts 가 long 을 못 읽는다는 문장은 없다(도움말의 「long 덱은 받지 않는다」 는 `cad_solid_merge_to_deck` 것).
  매뉴얼 48.4 에 읽는 폭을, 48.2 에 아래 한계를 적었다. 도움말 글은 건드리지 않았다(`HelpCatalogData.inc` 그대로).
- 단위 시험 231/231 · 회귀 133 파일 전부 rc 0(gmsh 환경 변수 둘을 준 채).

## 8. 주 덱과 폭이 다른 인클루드(C-3 — 재기만 했다)
같은 모델을 주 덱(절점 · 요소)과 인클루드(파트 · 섹션 · 재질 · 아워글라스 · 세트)로 나눠 일곱 꼴로 쟀다. 예전 판은 설치된 바이너리(248ec9bc).

| 꼴 | 고친 판 | 예전 판 |
|---|---|---|
| a 표준 + 표준(머리 없음) | rc 0 · 기준과 같다 | rc 0 · 기준과 같다 |
| b long + long(머리 없음) | rc 0 · 기준과 같다 | rc 1 「No *PART」 |
| c long + long(제 `*KEYWORD LONG=Y`) | rc 0 · 기준과 같다 | rc 1 「No *PART」 |
| d long + 표준(제 `*KEYWORD`) | **rc 0 · 폭이 섞인 산출** | 같다(산출 바이트 같음) |
| e 표준 + long(제 `*KEYWORD LONG=Y`) | rc 1 미정의 파트 4 | rc 1 「No *PART」 |
| f 표준 + long(머리 없음 · `*INCLUDE +`) | rc 1 「No *PART」 | rc 1 「No *PART」 |
| g long + 표준(머리 없음 · `*INCLUDE -`) | **rc 0 · 폭이 섞인 산출** | 같다(산출 바이트 같음) |

- d · g 의 산출은 `*KEYWORD LONG=Y` 한 줄 아래에 인클루드의 10칸 `*PART` · `*SECTION` · `*MAT` 카드를 접미사 없이 싣는다. 보고는 ok true ·
  되읽기 0 이다. LS-DYNA 는 그 카드를 20칸으로 읽는다(g 는 매뉴얼이 허락하는 입력이다 — Vol_I 19349-19351. d 는 인클루드 제 `*KEYWORD` 가
  먹는지 매뉴얼에 없다 — `IncludeClosure.h` 의 앞선 정리). 이번 고침으로 생긴 것이 아니다(두 판 산출이 바이트로 같다).
- 고쳐 쓰는 op 의 `flatten_includes: true` 가 쓰는 정본(`include_closure::inlined`)은 이 두 꼴을 「한 폭으로 펼칠 수 없다」 로 거절한다.
  extract-parts 는 그 관문을 거치지 않는다(덱을 담지 않고 흘려 읽는다).
- 흔한가 — 앞선 조사에서 실사용 88 장 가운데 폭이 갈린 덱은 0 이었다(`IncludeClosure.h` 주석).
- **고치지 않았다**(계획 3절 — 범위 밖). 거절 관문을 둘지는 사용자 결정으로 남긴다(체크리스트 C-4) — 두면 지금 rc 0 인 d · g 가 rc 1 이 된다.
