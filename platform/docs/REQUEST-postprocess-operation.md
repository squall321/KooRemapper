# 요청 — 후처리를 DynaForge 안으로 옮길 때의 **계약 모양**

**보내는 곳** HWAX Portal · 절차(procedures) 기능
**날짜** 2026-09-16
**한 줄** 후처리(KooD3plot)가 이쪽으로 온다고 들었습니다. **무엇을 만들어 달라는 요청이
아니라**, 어떤 모양으로 오면 우리 절차가 **한 줄도 안 고치고** 흡수하는지 적습니다.
**성격** 인터페이스 합의 요청입니다. 결정은 이 리포가 합니다.

---

## 1. 왜 지금 쓰나

포털에 **절차**(한 번 한 일을 굳혀 대상만 바꿔 재생하는 것)를 만들고 있습니다. 두 번째
실전이 **낙하·충격(R2)** 인데, 그 흐름이 이렇습니다.

> 잡 제출 → (기다림) → **후처리** → 리포트 반입 → 판독(`report_summary`·
> `report_worst_cases`·`report_directional`) → 보고서

**판독은 이미 이 리포에 있습니다.** 없는 것은 가운데 **후처리** 한 칸뿐이고, 지금은
smart-twin-mcp `job_postprocess`(KooChainRun → KooD3plotReader)에 있습니다.

그래서 우리는 절차를 **읽는 쪽으로만** 써 두고 얻는 쪽을 `report_id` 변수 하나로 좁혔습니다.
후처리가 이쪽으로 오면 **앞에 단계 하나만 더하면** 되게요. 다만 그 "단계 하나" 가
어떤 모양이냐에 따라 우리가 할 일이 **0줄이거나 꽤 됩니다.** 그 차이를 적습니다.

## 2. 우리가 확인한 현재 상태 (2026-09-16 실측)

| | |
|---|---|
| `list_operations` | **47종** — 후처리 관련 **0건** |
| 판독 도구 | `report_summary`·`report_worst_cases`·`report_directional`·`ingest_report` 이미 있음 |
| 파일 반입 | `report_upload_instructions` 가 REST intake 를 안내(MCP 로 본문 안 나름 — 맞는 판단입니다) |
| 실측 리포트 크기 | `sphere_report.html` **9.8MB** · `impact_report.html` **7.9MB** |

## 3. 세 갈래 — 어느 쪽이든 되지만 우리 일이 다릅니다

### ① `run_operation` 의 연산으로 온다 → **우리가 한 줄도 안 고칩니다** (가장 좋음)

`operation="postprocess"` 로 오고 `describe_operation("postprocess")` 가 `args_schema` 를
주면 끝입니다. 이유 —

- 포털 절차의 **2단 도구 등록부**에 DynaForge 가 **이미 들어 있습니다**
  (`run_operation` + `describe_operation`, 연산 47종). 등록부는 데이터라 항목이 늘어도
  코드가 안 바뀝니다.
- 그 `args_schema` 로 절차가 **저장 시점에** 인자를 검증합니다. 오타가 실행 때가 아니라
  저장 때 잡힙니다.

### ② 독립 도구로 온다 → **인자 스키마가 필요합니다**

지금 `job_postprocess` 는 `args` 가 **속성 없는 자유 object** 하나이고, `mode`
(`all|deep|sphere`)가 **산문에만** 적혀 있습니다. 그 모양 그대로 오면 우리는 오타를
저장 시점에 못 잡습니다.
(2026-09-17 정정 — 처음엔 "`mode="spehre"` 가 조용히 통과해 실행 때 기본값으로 돈다" 고 적었으나 틀렸습니다.
SmartTwinMCP 서버가 `args.schema.json` enum 으로 **실행 전에** 거절합니다. 맞는 것은 게이트웨이에 보이는 시그니처가
자유 object 라 **절차를 저장하는 시점에** 못 잡는다는 데까지입니다.)

**부탁**: 자유 object 대신 `mode` 를 **enum 으로 선언된 인자**로 내 주십시오.
(같은 부류의 결손을 STC 템플릿에서도 올려 뒀습니다 — 자유 object 는 검증이 통째로 꺼집니다.)

### ③ 오래 걸린다 → 제출·회수로 **자동으로 갈립니다**

전각도 낙하는 Run 이 수십~수백이라 120초를 넘길 수 있습니다. 포털 절차는 `expect: job`
을 **저장 거절**로 두어 제출·회수 두 절차로 갈리게 강제합니다(게이트웨이 호출 상한이
120초이고, 넘기면 그 백엔드 영속 세션이 재연결되며 **같은 백엔드에 걸린 챗·심의 호출까지
끊깁니다**). 그래서 오래 걸리는 것 자체는 문제가 아니고, **상태를 물을 도구**만 있으면 됩니다.

**부탁**: 오래 걸리면 `job_id` 를 즉시 돌려주고 상태 조회 도구를 함께 주십시오.
이미 `job_status`·`get_job` 계열이 있으니 그대로여도 됩니다.

## 4. 어느 쪽이든 지켜 주시면 좋은 것 넷

`bend_profile`(StepForge)이 쓸 만한 이유가 이 넷이라고 봅니다. 후처리도 같으면 절차의
`save` 경로가 앱마다 달라지지 않습니다.

1. **지어내지 않는다** — 산출이 없으면 값을 내지 말고 **이유**를 낸다(`ok: false` + `reason`).
   ⚠ 실제로 겪었습니다: 구버전 SIF 가 `impact_report` 를 **`exit 0` 으로 조용히 건너뛰었고**,
   산출이 없는데 성공으로 보였습니다. 그게 이 스택에서 가장 비싼 실패 모양입니다.
2. **성패를 본문으로 말한다** — `{"ok": false, ...}` 나 `{"status": "error"}` 로.
   우리 판정기가 그 셋(`ok`·`status`·`errors`)을 봅니다. `exit_code` 도 봅니다.
3. **경고를 버리지 않는다** — 결과는 정상인데 경고만이 유일한 신호인 자리가 있습니다
   (적층 쪽 `W120` 처럼). `warnings[]` 로 주시면 절차가 비교표에 실어 보여 줍니다.
4. **산출 위치를 구조로 낸다** — `report_id` 든 경로든, 다음 단계가 **한 칸에서** 꺼낼 수
   있게. 산문에 섞여 오면 사람이 매번 파싱합니다.

## 5. 우리가 **안 정한 것** — 이 리포가 정해 주십시오

정직하게, 후처리 내부를 모릅니다. 아래는 물음이지 지시가 아닙니다.

- **반입까지 한 번에 하나요, 후처리와 반입이 두 단계인가요.** 우리는 어느 쪽이든 됩니다 —
  다만 한 번에 하면 절차가 한 단계 짧아지고, 두 단계면 중간에 사람이 볼 자리가 생깁니다.
- **`mode` 의 실제 값 집합.** 산문에는 `all|deep|sphere` 인데 부분충격도 그 어휘인가요?
- **입력이 무엇인가요** — Run 디렉터리 경로? 잡 id? 둘 다?
- **9.8MB 리포트를 이쪽이 직접 읽나요, REST intake 를 그대로 쓰나요.** 후자면 우리 절차는
  지금 모양 그대로입니다.

## 6. 급한가

**아닙니다.** 이것 없이도 R2 절차는 **읽는 쪽으로** 섭니다. 다만 얻는 쪽이 비어 있어
사람이 매번 손으로 채웁니다. 그리고 지금 사슬(REST 명령·파일 경로·`job_postprocess` 인자)을
절차에 박아 두면 **옮겨진 뒤 그 절차가 전부 거짓말이 됩니다** — 그래서 일부러 비워 두고
이 문서를 씁니다.

## 7. 2026-09-17 — 사용자가 정한 모양

§5 의 물음 가운데 둘이 정해졌습니다(HWAXPortal `docs/procedures/context-notes.md` W-93).

1. **DynaForge 가 클러스터에 후처리 잡을 걸고 리포트 HTML 만 받습니다.** d3plot(잡 하나 37~50GB, dev 실측)은 나르지
   않습니다. 끝나면 `sphere_report.html`·`impact_report.html`(약 10MB)을 받아 반입하고 `report_id` 를 냅니다 —
   §5 "반입까지 한 번에" 는 **예**, "9.8MB 를 직접 읽나" 는 **클러스터에서 가져와 직접 반입**입니다.
2. **클러스터로 가는 길은 둘 다 되게, 기본은 대시보드 REST 입니다.** ssh(cae00 → stc → stcx)는 대체 길입니다.
   - REST 를 기본으로 쓰려면 대시보드 파일 REST(`/api/jobs/<id>/files/download`)의 **인증·소유 검사가 먼저** 필요합니다 —
     지금은 토큰 없이도 통과합니다(KooSlurm 쪽 일). 그 결함에 기대는 구현은 피해 주십시오.
   - ssh 대체 길에는 **연결·전체 시간 상한**을 두어 주십시오. 기존 SmartTwinMCP 배선에는 ConnectTimeout 이 없어 멈출 수 있습니다.
3. **끝남을 알 방법** — 대시보드에 완료 알림이 없고, 후처리가 실패해도 드라이버는 `COMPLETED 0:0` 입니다. 클러스터 템플릿이
   리포트 잡을 기다린 뒤 **귀환 매니페스트**(`output/return_manifest.json`: 잡 id·리포트별 경로·크기·sha256·있음/없음과 이유·
   후처리 rc)를 쓰게 하는 안을 KooSlurm·pyKooCAE 에 함께 올릴 예정입니다. 연산은 그 한 장을 보면 됩니다(§4-1 "지어내지 않는다").
4. **부분충격은 지금 리포트가 안 생깁니다** — `smarttwin_submit` 부분충격 잡에서 prepare 가 `impact_report.sh` 를 만들지 않습니다
   (pyKooCAE 쪽 일). 그 전까지 impact 후처리는 "없음·이유" 로 답해 주십시오.

**아직 안 정한 것 — 자동으로 반입한 리포트의 명의.** 리포트가 `user_id` 로 소유되고 관리자가 아니면 자기 것만 보이므로,
명의가 곧 "누가 찾나" 입니다. 포털 쪽에서 사용자에게 선택지 다섯을 올렸습니다(W-93 표).
① 후처리를 부른 사람 ② 제출 때 예약한 사람(권장 — 게이트웨이 위임 호출의 신원을 예약 원장에 적어 두고, 끝나면 그 명의로 반입)
③ 대시보드 제출자(`/auth/sso` 로 대리 발급 — 게이트웨이 시크릿 보관·클라이언트 이름 추가 필요) ④ 서비스 계정 + 공유 범위
⑤ 서비스 계정 보관 후 제출자가 가져가기. 정해지면 이 절에 이어 적겠습니다.

### 참고 — 이 요청이 나온 경위

포털 쪽에서 **"재현을 시도하면 결손이 드러난다"** 는 고리를 만들고 있습니다
(`HWAXPortal/docs/procedures/PLAN.md` §9-2). 챗에서 한 일을 절차로 펴 보고, 안 펴지는
칸을 결손으로 올려 **그 역할의 앱에 요청**하는 방식입니다. 같은 고리가 StepForge 로 한 번
갔고(`StepForge/docs/REQUEST-stackup-profile.md`), 이번이 두 번째입니다.

⚠ 한 번 헛짚은 적이 있어 적어 둡니다. 게이트웨이 도구 466개를 훑고 "DynaForge 에 물성
갱신 도구가 없다" 고 판단했는데 **틀렸습니다** — `run_operation` 뒤에 `matdb`·`matswap` 이
있었습니다. 도구가 아니라 연산이라 목록에도 검색에도 안 나왔습니다.
**이번도 그럴 수 있습니다. 이미 되는 길이 있으면 알려 주십시오** — 그러면 요청을 접고
그 길을 씁니다.
